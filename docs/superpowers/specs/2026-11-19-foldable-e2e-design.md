# 폴더블 대응과 E2E 테스트 환경 — 설계

2026-11-19, 사용자 승인됨. 대상 기기는 아이폰 Duo와 갤럭시 Z 폴드8. 테스트를 먼저 쓰고(TDD) 그 테스트가 통과하도록 화면을 고친다.

## 왜 하는가

- 폴더블에서 화면이 실제로 깨진다(아래 "지금 상태"). 지금은 사람이 기기를 띄워 눈으로 봐야만 알 수 있다.
- 단위 테스트만 통과시키고 닫았다가 실기기에서 재발한 사례가 있다(달력 선택 원 #1698 → #1717, 안드로이드 캐릭터 정지 이미지 #1721). 화면 크기·플랫폼별 회귀를 PR에서 잡는 장치가 없다.
- 사용자가 전달받은 조건: 아이폰 Duo를 제대로 지원하지 않으면 App Store 심사를 통과시켜 주지 않는다(2026-11-19 사용자 전언, 애플 문서로 대조하지는 않았다). 그래서 일부 화면만이 아니라 앱 전체가 대상이다.
- 프론트엔드 플랫폼 직군 포트폴리오로 쓴다. "무엇을 만들었나"가 아니라 "회귀를 몇 건 잡았나"를 수치로 남긴다.

## 지금 상태 (2026-11-19 실측)

기기 화면 크기:

| 기기           | 상태 | 크기                         | 출처                                         |
| -------------- | ---- | ---------------------------- | -------------------------------------------- |
| 아이폰 Duo     | 접힘 | 466×678pt (@3x)              | Xcode 27.2 시뮬레이터 프로필                 |
| 아이폰 Duo     | 펼침 | 951×669pt (@3x, 가로로 넓다) | 시뮬레이터 스크린샷 2853×2007px              |
| 갤럭시 Z 폴드8 | 커버 | 1248×1972px (10:16)          | 제조사 공개 사양. dp 값은 미측정             |
| 갤럭시 Z 폴드8 | 펼침 | 2448×1848px (4:3)            | 제조사 공개 사양. dp 값과 기본 방향은 미측정 |
| 기준 폰        | —    | 402×874pt (아이폰 17)        | —                                            |

접힌 Duo에서 본 문제(시뮬레이터, #1785 이전 빌드):

- 화면 오른쪽 위에 시스템 표시 영역(카메라 구멍·시계·와이파이, 세로 알약 모양, 대략 폭 50pt·높이 135pt)이 있고 앱이 이 자리를 피하지 않는다.
  - 크리스마스 출석 모달의 닫기 버튼이 그 밑에 깔려 누르면 제어 센터가 열린다. 모달 바깥을 눌러도 닫히지 않는다. 사실상 닫을 수 없다.
  - 달력의 다음 달 화살표와 '할 일' 탭, 집의 채팅 버튼, 내 정보의 설정 버튼이 가려진다.
- 화면이 넓고 짧아(비율 0.69) 폭에 맞춰 커지는 그림이 세로를 다 차지한다.
  - 방: 방 그림이 678 중 약 570을 차지해 '오늘의 할 일'이 제목 한 줄만 보인다.
  - 집: 2층이 탭 바 뒤로 잘린다. 달력: 그날 할 일이 한두 줄만 보인다.
  - 방 꾸미기(웹 466×678에서 확인): 가구 목록이 '적용하기' 버튼 밑에 가려 첫 화면에서 안 보인다.

2026-11-20 추가 실측(작은 네이티브 확인용 앱으로 `window.safeAreaInsets`를 읽음): Duo는 접힘·펼침 모두 **top 0, bottom 34, right 84**다. 오른쪽 위에 보이는 시스템 표시 영역은 알약 크기가 아니라 오른쪽 84pt 전체 높이의 안전 영역 인셋으로 나온다. 그래서 배치에 쓸 수 있는 폭은 접힘 382, 펼침 867이다. 앱은 가로 인셋을 전혀 보지 않고 있었다.

2026-11-20 진행: 접힌 Duo의 결함 8건을 모두 고쳤다. 가로 안전 영역 인셋(#1792)으로 4건, 짧은 화면(배치 폭/높이 ≥ 0.5)에서 그림 높이를 화면 절반에 맞추는 것으로 4건. 방 양옆은 같은 벽지·바닥 그림을 흐리게 깔아 채운다(서버 카탈로그의 벽지 `color`는 그림과 무관한 색조라 단색 채움은 경계가 드러난다). 이 규칙은 iPhone SE(375×667)에도 적용된다.

2026-11-23 진행: 펼친 화면 2단의 첫 단계 — 터치 기기는 배치 폭 **640** 이상이면 두 칸 1:1로 창을 다 쓴다(`TOUCH_SPLIT_MIN_WIDTH`, `splitFill`). 아래 "600 이상"과 "칸이 320 아래면 켜지 않는다"가 1:1 배치에서 서로 어긋나 640으로 정했다. 방·달력·방 꾸미기에 적용했고, 집·피드·내 정보와 왼쪽 세로 탭 줄은 다음 단계다. 접힌 화면은 좌석 이름표(#1798)와 시스템 표시 띠 배경(#1799·#1800)까지 마쳤다.

펼친 화면:

- #1785(2026-11-15 머지)가 폰보다 넓은 창(480 초과)에서 앱을 가운데 480 기둥으로 그리게 했다. 네이티브에서는 2단을 꺼 두었다(`use-app-frame.ts`의 `split`은 `os === 'web'`일 때만).
- 그래서 지금 `dev`에서는 펼친 화면 양옆이 여백으로 남는다. #1785 이후 빌드로 Duo·폴드8에서 직접 확인하지는 않았다.

다른 사람이 하고 있는 것:

- #1787(열림): iOS 27 SDK의 UIScene 수명주기 채택. **이 설계의 범위가 아니다.** 다만 Xcode 27로 만든 로컬 빌드는 #1787 없이 iOS 27 시뮬레이터에서 실행 즉시 죽으므로, Duo 시뮬레이터 확인은 #1787 머지 이후 빌드로 한다(그 전에는 git에 안 잡히는 `ios/` 로컬 패치로).

## 목표

1. **E2E 테스트 환경**: 웹(Playwright)은 PR마다 CI에서, 네이티브(iOS·Android)는 로컬에서 한 명령으로 돈다.
2. **접힌 화면(Duo 접힘, 폴드8 커버)**: 시스템 영역에 가려지는 조작 요소가 없고, 모든 모달을 닫을 수 있고, 각 화면의 핵심 내용이 첫 화면에 보인다. 그림은 화면 높이의 절반쯤으로 제한하고 비율을 지키며, 그림 양옆은 그림과 같은 배경색으로 채워 잘린 것처럼 보이지 않게 한다.
3. **펼친 화면(Duo 펼침, 폴드8 펼침)**: **앱의 모든 화면이** 양옆 빈 여백 없이 화면을 채운다. 다섯 탭은 좌우 2단, 그림(방·집)은 원래 비율 그대로.

사용자가 정한 완료 기준: "접힘과 펼침 모두에서 여백이 없고 비율이 맞는다."

## 하지 않는 것

- 갤럭시 Z 플립, 아이패드, 폰 가로 모드.
- 반쯤 접은 자세(탁자에 세워 둔 상태)와 힌지 위치를 아는 배치.
- UIScene 채택(#1787), Xcode·EAS 빌드 이미지 변경.
- 네이티브 E2E의 CI 상시 실행(EAS 쿼터와 macOS 러너 비용. 1단계는 로컬 실행).
- 폰 화면 배치 변경, 데스크톱 웹에서 방·달력의 기존 2단 동작 변경.

## 이러면 실패다

- 기준 폰(402×874)의 화면이 달라진다. 데스크톱 웹의 방·달력 2단이 달라진다.
- 펼친 화면에서 가운데 기둥과 빈 여백으로 남는 화면이 하나라도 있다.
- 테스트가 사용자 본인 계정(userId 4)이나 운영 데이터를 바꾼다.
- JS만 고치는 PR에 런타임 지문이 바뀌는 변경(`app.json`, `package.json`의 `scripts`, `.gitignore`, `plugins/`)이 섞여 OTA가 끊긴다.
- 스크린샷 비교에만 기대서, 글꼴 렌더링 차이로 흔들리는 테스트가 된다.

## 내가 정한 것 (사용자가 뒤집을 수 있다)

테스트 구조:

- **웹 E2E는 Playwright**(이미 설치됨, 지금은 Storybook용). 화면 크기를 프로젝트로 둔다: 기준 폰, Duo 접힘, Duo 펼침, 폴드8 커버, 폴드8 펼침.
- **배치 테스트는 API를 가로채 고정 응답으로 돌린다.** 서버와 계정에 의존하지 않아 결과가 흔들리지 않고, 실계정을 건드릴 일이 없다. 고정 응답은 `src/mocks/fixtures.ts`와 어댑터 계약에서 만든다.
- **배치는 스크린샷이 아니라 수치로 단언한다.** 요소의 위치·크기를 읽어 아래 규칙을 검사한다.
  1. 조작 요소가 기기별 "가려지는 영역"(시스템 표시 영역, 탭 바)과 겹치지 않는다.
  2. 열린 모달의 닫기 버튼이 화면 안에 있고 누를 수 있다.
  3. 방·집 그림의 가로세로 비가 렌더 계약(`room-render-contract`) 값과 1% 안에서 같고, 화면 밖으로 잘리지 않는다.
  4. 펼친 화면에서 두 칸이 나란히 있고, 내용이 차지하는 폭이 창 폭과 같다(양옆 여백 0).
  5. 각 탭의 핵심 내용(할 일 첫 항목, 가구 목록 첫 줄 등)이 첫 화면 안에 있다.
  6. 가로 스크롤이 생기지 않는다.
- 기기별 시스템 영역은 웹에서 재현되지 않으므로, 테스트가 안전 영역 값을 주입한다(주입 지점은 빌더가 정한다).
- **네이티브는 Maestro로 스모크만**: 실행, 로그인된 상태, 다섯 탭이 각각 핵심 요소를 그리는지. Maestro가 Xcode 27.2·iOS 27에서 도는지는 미확인이다. 안 되면 `simctl` 스크린샷과 `idb` 입력 스크립트로 대신한다(펼친 Duo에서는 `idb` 탭이 닿지 않는 것을 확인했다. 그 경우 시작 탭 저장값 `rougether.start-tab`을 바꿔 재실행한다).
- 실서버를 치는 스모크는 1단계에 넣지 않는다. 넣으려면 전용 테스트 계정이 필요하고, 계정 생성은 사용자 결정이다.

2단 기준:

- 네이티브에서 창 폭이 **600 이상이면 2단**. 폴드8 펼침이 세로로 잡히면 폭이 약 700dp라 840 기준으로는 2단이 안 된다. 실제 dp 값은 에뮬레이터에서 먼저 재고, 다르면 이 값을 고친다.
- 탭 바를 왼쪽 세로 줄로 두는 것은 폭 840 이상에서만. 그보다 좁은 2단(폴드8 세로 펼침 추정 약 700)은 아래 탭 바를 유지한다(칸 하나가 300 아래로 내려가지 않게).
- 데스크톱 웹(마우스)은 지금 기준(960)을 그대로 둔다.
- **터치가 주 입력인 모바일 웹은 네이티브와 같은 600 기준을 따른다.** 판정은 `resolveAppFrame` 한 곳에서 하고, 입력으로 "터치 기기인가"를 받는다. 이렇게 해야 Playwright의 폴더블 프로젝트(터치 켬)가 네이티브와 같은 2단을 그려 규칙 4를 웹에서 검증할 수 있고, 폴더블로 웹앱을 여는 사용자도 같은 화면을 본다. 기준값 자체는 단위 테스트로 따로 잠근다.
- 이 기준이면 안드로이드 태블릿도 2단이 된다. 받아들인다.
- 폭 600~839의 좁은 2단은 시안과 같은 구성을 두 칸 1:1로 쓴다. 칸 하나가 320 아래로 내려가는 폭이면 2단을 켜지 않는다.
- 세로 고정(`app.json`의 `orientation`)은 건드리지 않는다. 펼친 Duo는 세로 고정 상태에서도 가로 화면 전체에 그려지는 것을 확인했다. 폴드8에서 OS가 앱을 띠 모양으로 가두는 것이 측정으로 확인되면, 그때 별도 `native-build` PR로 제안하고 사용자 승인을 받는다(이 설계의 다섯 PR에는 넣지 않는다).

오른쪽 칸의 동작:

- 피드는 탭에 들어오면 목록의 첫 글을 고른 상태로 시작한다. 목록이 비면 오른쪽 칸에 빈 상태 안내를 둔다.
- 내 정보는 오른쪽 칸이 메뉴 목록으로 시작한다. 메뉴 항목, 설정, 프로필 편집, 재화 내역은 오른쪽 칸 안에서 열리고 뒤로 가면 메뉴 목록으로 돌아온다. 크리스마스처럼 원래 모달인 것은 모달 그대로 둔다.
- 집 그림 비율은 방 렌더 계약이 아니라 `src/resources/house-frame.ts`의 층수별 값으로 단언한다.
- "데스크톱 웹 불변"을 지키기 위해 Playwright에 데스크톱 프로젝트도 둔다. E2E CI 작업은 처음에는 필수 체크와 분리해 두고, 2주간 흔들림이 없으면 필수로 올린다.

구현 순서(전부 JS만, 번호 하나가 PR 하나 이상):

1. 웹 E2E 기반: Playwright 설정, 화면 크기 프로젝트, API 가로채기, 기준 폰에서 통과하는 배치 규칙 테스트, CI 작업.
2. 접힌 화면: 규칙 1·2·3·5의 실패 테스트 → 수정.
3. 펼친 화면 2단(방·달력): 네이티브에서 2단 켜기, 규칙 3·4 테스트 → 수정.
4. 펼친 화면 2단(집·피드·내 정보): 시안 구현. 데스크톱 웹 포함.
5. 탭이 아닌 화면 전수 목록을 만들고(라우트와 `screens/` 기준), 화면마다 펼친 화면에서의 배치를 정한다: 2단으로 나눌 화면, 한 칸을 넓게 쓰는 화면, 시트·모달로 뜨는 화면. 목록과 배치안은 구현 전에 사용자에게 보인다.
6. 5의 목록을 도메인별로 묶어 PR을 나눈다(집·채팅 / 방 꾸미기·가구 / 뽑기·미니게임 / 내 정보·설정 / 로그인·온보딩). 묶음마다 규칙 4·6의 실패 테스트 → 수정.
7. 네이티브 스모크와 기기 확인(Duo 시뮬레이터 접힘·펼침, 폴드8 크기 에뮬레이터), 포트폴리오 사례 기록.

실기기에서 완료되려면 필요한 것(이 설계 밖):

- #1787에 따르면 Duo에서 전체 화면으로 그려지려면 iOS 27.1 SDK로 빌드해야 한다. 즉 스토어 빌드가 Xcode 27로 올라가야 하고, 그러려면 #1787(UIScene)이 먼저 들어가야 한다. 이 설계의 JS 변경은 그 빌드가 나온 뒤에야 실제 Duo에서 효과가 난다. 그 전에는 로컬 Xcode 27 빌드와 시뮬레이터로 확인한다.
