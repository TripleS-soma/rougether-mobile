# 제작 가구의 원본 보관과 고정가 판매 전환

- 날짜: 2026-11-05 / 영역: room / 관련 [앱 #1628](https://github.com/TripleS-soma/rougether-mobile/issues/1628), [서버 #488](https://github.com/TripleS-soma/rougether-server/pull/488)
- 키워드: 소유권, 멱등 구매, 트랜잭션, 운영 데이터 전환, OTA 런타임

## 배경

습관 형성을 돕는 소셜 루틴 앱에서 사용자가 AI로 만든 가구를 자기 방에 보관하고 다른 사용자에게 판매할 수 있었다. 기존 거래소는 구매, 판매 주문을 매칭하고 보유 가구를 판매 에스크로에 맡기는 구조였다.

## 문제 (증상)

사용자는 생성한 가구가 사라졌다고 느꼈다. 제작자가 자기 원본을 판매 등록해도 계속 보관할 것으로 기대했지만, 보유분 판매는 가구함에서 숨기고 방 배치도 제거했다.

## 원인 분석 (가설 → 검증 과정)

생성 실패와 서버 재시작 가능성을 먼저 확인했다. 운영 생성 이력에서는 생성 성공과 보관함 지급이 확인됐고, 이후 동일 가구의 보유분 판매 주문이 확인됐다. 가구 삭제처럼 보인 현상은 판매 에스크로 처리와 연결됐다. 해당 주문을 정상 취소 경로로 처리해 원본을 반환했다. 취소는 가구함을 복구하지만 이전 방 배치까지 복원하지는 않는다.

## 해결

제작자는 원본을 유지하고 가격만 설정해 수량 제한 없이 판매하도록 바꿨다. 구매자는 표시 가격에 같은 가구를 한 번만 구매하고 재판매는 제공하지 않는다. 구매 확인 시점의 가격과 requestId를 보내며, 응답 유실 재시도는 같은 키를 재사용한다. 가격이 달라지면 서버가 구매를 거절한다.

서버는 구매자 차감, 제작자 지급, 가구 지급, 영수증, 원장을 하나의 트랜잭션으로 처리한다. 구 주문과 미반환 에스크로가 남아 있으면 새 구매를 차단하고 기존 엔진의 취소 경로로 정리한다. 제작자 가격을 임의로 채우지 않아 기존 상품은 제작자가 가격을 설정해야 새 목록에 나타난다.

앱 배포에서는 현재 dev의 네이티브 입력이 기존 설치본과 다름을 확인했다. 기존 production 소스에 JS 변경만 적용한 배포 후보를 별도로 준비하고, 플랫폼별 런타임이 목표와 일치할 때만 OTA를 게시하는 기존 절차를 사용한다.

## 결과 (수치)

서버 PR #488의 CI와 CodeQL이 통과했고 EC2 배포가 완료됐다. 실제 실행 중인 user-api, admin-api, batch 이미지가 머지 커밋과 일치했다. 운영 DB에서 V95 적용 성공, 남은 OPEN 주문 0건, PENDING 명령 0건, 미반환 오류 0건을 확인했다. 복구 대상 가구도 보관 상태였다. 새 구매는 운영 사용자 자산으로 시험하지 않았으며 동시 구매, 재시도와 실패 롤백은 통합 테스트로 검증했다.

이 문서 작성 시점에는 앱 기능 커밋의 CI가 통과했고 머지와 OTA 게시를 진행하기 전이다. 앱 배포 완료나 실제 단말 수신을 이 결과에 포함하지 않는다.

## 배운 점 / 재발 방지

보관함에서 보이지 않는 현상은 생성 실패 외에 판매 예약 같은 상태 전이에서도 생긴다. 생성, 지급, 판매를 같은 가구 식별자로 연결해 확인해야 한다. 거래소를 단순화할 때는 화면뿐 아니라 기존 에스크로의 반환과 새 구매의 시작 조건을 함께 설계해야 한다. OTA 성공 여부도 게시 영수증과 설치본 런타임의 일치를 나눠 확인한다.
