# OTA 발행 성공과 실제 스토어 설치본의 기능 도달을 구분한 사례

- 날짜: 2026-11-11 / 영역: 모바일 배포 / 관련 이슈: #1738
- 키워드: Expo Updates, runtime fingerprint, 핫픽스 이식, 배포 검증

## 배경

게시물 작성자가 참여하는 집 중 하나를 골라 입주 신청하는 기능을 앱에 추가했다. Android 기존 설치본과 최신 런타임, iOS 개발 소스의 런타임에 각각 OTA를 발행했다.

## 문제 (증상)

사용자가 스토어 iOS 앱의 게시물 상세 화면을 보내며 입주 신청 버튼이 없다고 보고했다. 앞선 배포 완료 안내는 실제 스토어 설치본의 도달 여부를 충분히 확인하지 않은 판단이었다.

## 원인 분석 (가설 → 검증 과정)

서버 health와 신규 입주 API 경로는 정상이다. 기존 iOS 발행 대상은 `05075342…`였지만 후속 스토어용 한글 입력 수정 OTA의 대상은 `05f36fe5…`였다. 스토어 대상 소스 `c8050972…`의 트리를 확인하자 입주 API 파일, 선택 시트와 게시물 버튼 배선이 없었다. 런타임이 맞는 발행이 없으므로 재실행만으로는 누락 기능을 받을 수 없었다.

## 해결

스토어 런타임의 최신 한글 입력 수정 소스에서 분기해 기존 입주 기능의 src 변경만 3-way로 이식했다. 네이티브 설정을 유지하고 지문이 `05f36fe5421731483bd31a9c083b8c5bed16a7c3`로 일치하는지 확인한 뒤 정식 hotfix-ota 워크플로로 발행했다. 원래 기능은 dev/main에 이미 들어 있어 중복 기능 PR은 만들지 않았다.

## 결과 (수치)

타입, 린트, 포맷 검사와 전체 447개 테스트 스위트, 3696개 테스트가 통과했다. 배포 워크플로 42985028947이 성공했다. production 업데이트 서버가 스토어 런타임 요청에 HTTP 200과 update ID `01a1c9ac-2b39-7f13-b7e2-ef2c00dc8a84`를 제공함을 확인했다. 사용자 기기의 실제 다운로드와 실행은 직접 확인하지 않았다.

## 배운 점 / 재발 방지

현재 main의 런타임과 스토어 설치본의 런타임은 별개다. 배포 완료는 대상 플랫폼 이름이나 워크플로 성공만으로 판단하지 않고, 설치본 런타임별 최신 배포 소스의 기능 포함 여부와 실제 manifest의 update ID를 함께 확인해야 한다. 기존 기기용 폰트 수정 같은 후속 OTA도 해당 런타임의 이전 기능을 유지하는지 비교해야 한다.
