# OTA 레인에서 이탈한 설치본에 말 걸기 — 버전 게이트를 JS만으로 만들기

- 2026-10-25 / infra(OTA·릴리스) / 이슈 #1572, PR #1573, 랜딩 PR #64·#65
- 키워드: Expo Updates, 런타임 지문, OTA 도달성, 네이티브 모듈과 지문, 실패 방향 설계, 원격 설정

## 배경

이 앱은 JS 변경을 EAS Update(OTA)로 배포한다. 스토어를 거치지 않아 배포가 빠른 대신, **네이티브 지문(runtime version)이 바뀌면 그 이전 바이너리는 OTA 레인에서 영구 이탈한다.** 승격을 몇 번 하든 `eas-release`를 몇 번 누르든 그 설치본에는 아무것도 닿지 않는다.

이탈한 설치본이 실제로 있었다. `src/constants/release-channel.ts`의 `PRE_UGC_RUNTIMES`에 1.5.3 두 바이너리의 지문(iOS `0ed984cc…` · Android `162a83fa…`)이 하드코딩돼 있고, 그 설치본은 피드·거래소가 꺼진 채 남는다. 1.5.4는 2026-10-07에 App Store에 출시됐는데(애플 공개 조회 API로 확인), 아직 1.5.3을 쓰는 사람에게는 2주 넘게 기능 두 개가 없는 앱이었다.

그런데 "스토어에서 업데이트하세요"를 말할 수단이 앱에 없었다. 스토어 URL 상수조차 없었다. 과거에 설정 화면에 OTA 적용 카드를 만들었다가(#1082·#1083) 다음 날 제거했는데(#1095, "OTA는 실행 시 자동 적용되므로 사용자 노출 필요가 없다"), 그때도 스토어 버전 게이트는 의도적으로 범위 밖이었다.

## 문제 (증상)

- 네이티브 지문이 바뀐 뒤 구 설치본은 기능이 빠진 상태로 고정되고, 우리가 알릴 방법이 없다.
- **이 기능 자체도 OTA로 전달된다.** 그래서 이미 이탈한 설치본은 이 게이트조차 받지 못한다 — 늦게 넣을수록 구제 못 하는 모집단이 커지는 구조였다.
- 그러니 **새 네이티브 모듈을 추가하면 안 된다.** 추가하는 순간 지문이 바뀌어 지금 설치본(1.5.4)에도 OTA로 못 가고, 다음 네이티브 빌드까지 효력이 생기지 않는다.

## 원인 분석 (가설 → 검증 과정)

핵심 질문은 하나였다. **JS만으로 "설치된 바이너리"를 식별할 수 있는가.**

세 후보를 차례로 검증했다.

1. `Constants.expoConfig.version` — **탈락.** OTA로 들어온 번들의 app.json 값이다. 1.5.4 바이너리에 1.5.5 번들이 OTA로 들어오면 1.5.5라고 답한다. 가리키는 것이 바이너리가 아니라 번들이다.

2. `Constants.platform.ios.buildNumber` / `Constants.platform.android.versionCode` — **절반만 통과.** 타입 정의상 둘 다 있고, iOS는 실제로 맞다. 코드 리뷰에서 "정말 바이너리 값인지 확인이 필요하다"는 지적이 와서 타입이 아니라 네이티브 구현을 읽었다.
   - iOS: `expo-constants/ios/EXConstantsService.m` — `[[NSBundle mainBundle] infoDictionary]["CFBundleVersion"]`. 설치된 바이너리의 Info.plist다. 통과.
   - Android: `expo-constants/android/.../ConstantsService.kt` — `"platform" to mapOf("android" to emptyMap())`. **빈 객체다.** 타입에 `versionCode: number`가 남아 있을 뿐 값이 오지 않는다(그래서 `@deprecated`가 `expo-application`을 가리키고 있었다).
   - 이 방식으로 먼저 구현을 끝냈던 상태였다. Android에서 영영 안 뜨고, 아무 로그도 남기지 않으므로 **침묵으로 실패**한다. 반쪽만 도는 게이트는 없는 것보다 나쁘다.

3. `expo-application`의 `nativeBuildVersion` — **탈락.** 정석이지만 네이티브 모듈이라 지문이 바뀐다. 위에서 적은 제약과 정면으로 충돌한다.

남은 것이 `Updates.runtimeVersion`이었다. 바이너리마다 박혀 있고, OTA로 바뀌면 그 OTA가 애초에 그 설치본에 오지 않으므로 논리적으로도 변할 수 없다. 두 플랫폼에서 동일하게 동작하고, 같은 레포의 `release-channel.ts`가 이미 같은 방식으로 바이너리를 식별하고 있었다 — 즉 선례가 코드 안에 있었는데 처음에 못 봤다.

## 해결

**판정 기준**: `Updates.runtimeVersion`을 원격 목록과 대조한다.

**원격 설정의 위치**: 서버가 아니라 랜딩(`rougether.com/app-version.json`)에 뒀다. 랜딩은 `main` 푸시가 즉시 배포라 **앱 배포 없이 목록만 고쳐 게이트를 켜고 끌 수 있다.** 서버 계약(spec)에 최소 버전 항목이 아예 없어서 서버 작업을 기다릴 필요도 없었다.

**목록의 방향** — 이 PR에서 가장 오래 고민한 설계 판단이다.

| 방향                                     | 잊었을 때 벌어지는 일                                               |
| ---------------------------------------- | ------------------------------------------------------------------- |
| 최신 지문만 적고 그 밖을 구버전으로 본다 | 새 빌드 지문을 적는 걸 잊으면 **최신 사용자에게 업데이트를 조른다** |
| 오래된 지문을 나열한다                   | 적는 걸 잊으면 **아무 일도 일어나지 않는다**                        |

운영 편의는 전자가 낫지만 후자를 골랐다. 사람이 잊는 건 기정사실이고, 잊었을 때 사용자에게 보이는 쪽으로 틀리면 안 된다. 대가는 "릴리스마다 직전 지문을 추가한다"는 절차이고 랜딩 README에 적었다.

**모르면 통과시킨다**를 전체에 적용했다. 설정 없음·조회 실패·지문 미확인(웹·개발 빌드·Expo Go)은 모두 통과다. 안내를 못 하는 것보다 쓰던 앱을 못 쓰게 만드는 쪽이 나쁘다.

**지문을 바꾸지 않기 위해 피한 것**: `Linking.canOpenURL`. iOS `LSApplicationQueriesSchemes`·Android manifest `<queries>` 선언이 필요해져 `app.json`을 건드리게 된다. `openURL`만 쓰고 실패하면 웹 주소로 떨어뜨렸고, 호출이 새어 들어오면 소스를 스캔하는 테스트가 막는다.

**원격이 주소를 들고 있지 않게** 했다. JSON이 스토어 URL까지 들고 있으면 그 파일 한 줄로 사용자를 임의의 주소로 보낼 수 있다. 원격은 어느 바이너리가 오래됐는지만 말하고, 어디로 보낼지는 바이너리의 상수가 정한다.

**막을 때도 앱 트리를 치우지 않는다.** 내비게이터를 조건부로 내리면 라우터 컨텍스트가 끊기고, 판정이 늦게 오는 순간(원격 조회가 끝나는 시점) 앱 트리 전체가 다시 마운트된다. 위에 덮되 **접근성 트리에서만** 걷어 낸다 — 오버레이는 터치만 막고 VoiceOver·TalkBack 포커스는 아래 화면으로 계속 들어가기 때문이다.

## 결과 (수치)

- **런타임 지문 머지 전후 동일** — 브랜치와 `origin/dev`에서 각각 실측. iOS `af939b5b…`, Android `4452ee66…`. 즉 기존 1.5.4 설치본이 이 기능을 OTA로 받는다.
- 앱 변경 14파일 / +1,031줄. 새 테스트 37건(판정 로직·훅·배선·화면), 전체 411 스위트 / 3,397건 통과.
- 랜딩은 정적 JSON 1개 + 스모크 검사 4건(지문 꼴, semver, 두 목록 겹침 금지).

## 배운 점 / 재발 방지

**타입이 있다고 값이 오는 건 아니다.** `Constants.platform.android.versionCode`는 타입 정의에 멀쩡히 있고 `@deprecated` 주석만 붙어 있었다. deprecated를 "곧 없어진다"로 읽고 넘겼는데 실제로는 **이미 값이 없었다.** 전제가 기능의 뿌리일 때는 타입이나 문서가 아니라 네이티브 구현을 읽어야 한다. `node_modules` 안의 `.m`·`.kt` 파일을 읽는 데 2분이 걸렸고, 그게 Android에서 통째로 안 도는 기능을 머지 직전에 막았다.

**침묵으로 실패하는 기능이 가장 위험하다.** 빌드 번호 방식은 Android에서 예외도, 로그도, 증상도 없이 그냥 아무것도 안 했다. "모르면 통과"는 안전한 기본값이지만, 그 통과가 **의도한 통과인지 고장난 통과인지 구분할 방법**을 같이 두지 않으면 고장을 영원히 모른다. 다음에 같은 모양을 만들면 "지문을 못 읽었다"를 한 번은 집계하는 쪽을 검토할 것이다.

**실패 방향을 설계 기준으로 쓸 수 있다.** 목록을 뒤집는 두 방식은 정상 동작이 똑같고 **잊었을 때만** 갈린다. 한쪽은 침묵, 한쪽은 최신 사용자를 조른다. 기능 비교로는 고를 수 없고 "틀릴 때 누가 아픈가"로 골랐다. 뒤집힌 값, 조회 실패, 파싱 실패도 같은 기준으로 정리했다.

**선례가 같은 레포에 있었다.** `release-channel.ts`가 이미 런타임 지문으로 바이너리를 식별하고 있었는데 처음에 `expo-constants`부터 찾았다. 플랫폼 API를 뒤지기 전에 **같은 문제를 이 코드베이스가 이미 어떻게 풀었는지** 먼저 봐야 했다.

## 후속

이슈 본문에 "1.5.3 이하 설치본은 구조적으로 구제 불가"라고 적었는데 **틀렸다.** `hotfix-ota` 워크플로가 `expected_runtime`으로 특정 런타임을 조준해 발행하고, 이 게이트는 JS만 바꾼다. 그러니 1.5.3을 빌드한 커밋에서 브랜치를 따 이 변경만 얹으면 그 지문으로 OTA가 나가고, 지금 이탈해 있는 사람들에게도 닿는다. 정상 레인에서 검증된 뒤에 할 일로 남겼다.

게이트는 아직 **꺼진 상태**다(목록이 비어 있음). 다음 네이티브 릴리스 때 직전 빌드의 지문을 `staleRuntimes`에 넣는 순간부터 동작한다.
