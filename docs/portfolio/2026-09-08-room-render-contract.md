# 같은 방이 화면마다 다르게 보이던 문제 — 하나의 렌더 계약과 "자리 박스" 두 겹 구조

- 2026-09-08 / room(방 렌더러) / 이슈 #397·#1194·#1099, PR #404·#1160·#1196·#1101
- 키워드: 렌더 계약(단일 진실 원천), 정규화 좌표계(normalized-rect), 하나의 문서·여러 뷰포트, 썸네일·미리보기 일관성, 스타일 병합 순서, 캐시 무효화

## 배경

Rougether의 "방"은 사용자가 꾸민 하나의 문서다. 벽지·바닥·가구 배치(x/y 중심 좌표·배율·회전)·캐릭터로 이루어지고,
서버에는 `FREE_V1` 형식으로 한 벌만 저장된다. 같은 방이 네 개의 뷰포트에 그려진다.

| 뷰포트       | 성격                            | 크기             |
| ------------ | ------------------------------- | ---------------- |
| 나의 방      | 인터랙티브(캐릭터 탭)           | 화면 전체 폭     |
| 꾸미기 화면  | 편집기 캔버스(드래그·크기 변경) | 화면 폭          |
| 친구 방      | 읽기 전용                       | 화면 폭          |
| 집 좌석 타일 | 읽기 전용 썸네일, 집 프레임 안  | 프레임 구멍 크기 |

캔버스 편집기에 빗대면 같은 문서를 편집 뷰, 보기 전용 뷰, 썸네일로 동시에 보여 주는 구조다.

좌표 규칙은 팀원이 먼저 정리했다. PR #404(2026-07-22, #397)에서 RN `Room` 렌더러의 방·표면·가구·캐릭터
규격을 버전이 붙은 JSON 계약(`room-render-contract.v1.json`)으로 추출했다. 관리자 웹의 가구 크기 스튜디오는
이 계약의 같은 사본(SHA-256 일치)을 쓰게 했다. 이후 PR #1160(2026-09-07)에서 방을 가로:세로 5:6 세로형으로 바꾸며
v2(`room-render-contract.v2.json`)가 됐다. 이때 저장된 좌표는 그대로 두고 표시만 바꿨다.

계약의 핵심은 다음과 같다(`src/components/room/room-render-contract.v2.json`).

- 좌표계: `normalized-rect`, 원점 왼쪽 위, 가구 기준점은 중심. x/y는 각 축 0~1이라 뷰포트 크기와 무관하다.
- 방: `aspectRatio` 5/6.
- 가구: 기본 폭은 방 폭의 0.28 × 배율, 배율 범위 0.5~3.5. 세로 경계는 폭/높이 비율로 보정한다(`furnitureClampBounds`).
- 캐릭터: `centerX` 0.5, `bottom` 0.16, `width` 0.42, `aspectRatio` 1, `contain`.

## 문제 (증상)

2026-09-08 사용자 보고(#1194)는 다음과 같았다.

- 집 좌석의 작은 방에서 캐릭터가 러그 위로 떠 보였다. 나의 방에서는 러그 위에 서 있었다.
- 꾸미기 화면의 캐릭터가 나의 방보다 작았다.

계약 수치는 모든 화면이 같았다. 그런데도 결과가 달랐다.

이틀 전(09-06, #1099)에는 다른 갈래의 불일치도 있었다. 꾸미기를 적용한 뒤 집 탭으로 가면 내 좌석 썸네일이
예전 방으로 보였다.

## 원인 분석 (가설 → 검증 과정)

1. **계약 값이 화면마다 다른가?** 그렇지 않았다. 네 화면 모두 `ROOM_RENDER_CONTRACT.character`에서 폭 42%,
   바닥 16%, 정사각을 가져왔다. 숫자가 아니라 숫자를 적용하는 구조를 의심했다.
2. **정상인 화면과 비교.** 나의 방(인터랙티브 분기)만 정상이었다. 이 분기는 `Pressable`(자리 박스, 계약 좌표)
   안에 `CharacterAvatar`를 `100% × 100%`로 채우는 두 겹 구조였다. 반면 비인터랙티브 분기(집 좌석·친구 방)와
   꾸미기 화면은 자리 스타일을 `CharacterAvatar`에 직접 넘겼다.
3. **스타일 병합 순서.** `CharacterAvatar`는 `[{ width: size, height: size }, style]` 순서로 스타일을 합치고,
   `size` 기본값은 96이다. 호출부 스타일은 `width`만 덮었다. 남은 명시 `height: 96`이 `aspectRatio: 1`보다
   우선하므로 실제 박스는 "폭 42% × 높이 96px"이었다.
   - 작은 방(집 좌석): 폭 42%가 96px보다 좁아 박스가 세로로 길어진다. `contain` 이미지가 박스 세로 중앙에
     놓여 바닥선에서 떠 보였다.
   - 큰 방(친구 방·꾸미기): 높이가 96px로 눌려 캐릭터가 나의 방보다 작게 그려졌다.

   같은 계약 값도 뷰포트 크기에 따라 다르게 틀어졌다. 문서 좌표계(정규화 비율)에 화면 좌표계(고정 px)가
   한 축에만 섞였기 때문이다.

4. **썸네일 갈래(#1099).** 집 좌석 미리보기 훅(`useMemberRoomPreviews`)은 집당 한 번만 불러오고 캐시했다.
   이 훅에는 꾸미기 저장 시 이 캐시를 무효화하는 경로가 없었다. 렌더 규칙은 맞았지만 그리는 데이터가 옛 버전이었다.

## 해결

- **#1196: 자리 박스와 내용물의 분리를 모든 뷰포트에 강제.** `Room`의 비인터랙티브 분기와 꾸미기 화면을
  나의 방과 같은 두 겹 구조로 바꿨다. 바깥 `View`에는 계약 좌표(42%/16%/정사각)만, 안쪽 아바타에는
  `{ width: '100%', height: '100%' }`만 준다. 계약 값은 바꾸지 않고, 계약을 적용하는 방법을 한 가지로 통일했다.
- **집 좌석도 같은 비율인지 확인.** 집 프레임은 `sourceAspectRatio × ROOM_ASPECT_RATIO`로 표시된다
  (`src/resources/house-frame.ts`). 원본 320×320 구멍이 5:6으로 그려지므로 썸네일 칸도 방과 같은 종횡비다.
  따라서 이 수정으로 네 뷰포트의 캐릭터 기하가 같아진다.
- **#1101: 미리보기 캐시 무효화.** 훅에 `invalidate()`를 추가하고 꾸미기 `onApply` 성공 경로에서 호출했다.
  다음 집 화면 진입 때 다시 불러오되, 새 응답이 올 때까지 기존 썸네일을 남겨 빈 타일 깜빡임을 막았다.
  내 좌석만 갱신하는 대신 전체 재조회를 택했다. 저장 응답을 미리보기 형태로 바꾸는 코드를 더하지 않기 위해서다.
- 같은 날의 곁가지: 나의 방만 모서리를 각지게 하려고 계약의 `borderRadiusPx`를 0으로 바꿨다(#1191).
  그러자 친구 방·꾸미기까지 바뀌어 16으로 되돌렸다(#1193). 대신 나의 방 화면 스타일이 덮어쓰게 했다.
  공통 계약에는 모든 뷰포트가 공유하는 값만 두고, 화면별 예외는 화면 쪽 오버라이드로 둔다는 경계를 이때 확인했다.

## 결과 (수치)

- #1196 변경량: +34 / −11, 파일 3개(`room.tsx`, `room-decor-screen.tsx`, `room.test.tsx`). JS만 바꿔 OTA로 배포했다.
- 방·꾸미기·집·친구 방 테스트 197개가 통과했다(PR 본문 기록).
- 새 회귀 테스트: 비인터랙티브 `Room`의 아바타는 100%/100%, 부모 자리 박스는 42%/16%/`aspectRatio` 1인지 단언한다.
- 계약 자체는 `room-render-contract.test.ts`가 고정한다. 모든 슬롯이 정규화 사각형 안에 있는지, 5/6 비율,
  캐릭터 규격, 배율 상한 3.5(0.28 × 3.5 = 방 폭 98%로, 방 안 클램프의 한계 1/0.28 ≈ 3.57 안쪽)를 확인한다.
- #1101: +38 / −1. 무효화 뒤 같은 집을 재조회하고 미리보기를 유지하는지 확인하는 훅 테스트를 추가했다.
- 실기기에서 수정 전후를 나란히 측정한 수치는 없다.

## 배운 점 / 재발 방지

- **단일 진실 원천은 값만으로는 부족하다.** 네 화면이 같은 계약 숫자를 읽었는데도 결과가 달랐던 이유는 적용 방식이
  화면마다 달랐기 때문이다. 계약은 값과 함께 "자리 박스는 계약 좌표, 내용물은 박스를 꽉 채운다"는 적용 구조까지
  포함해야 한다.
- **정규화 좌표계에 고정 px 기본값이 한 축이라도 섞이면, 뷰포트 크기에 따라 다른 방향으로 틀어진다.** 작은 썸네일에서는
  뜨고 큰 캔버스에서는 작아졌다. 증상이 정반대라 처음에는 서로 다른 버그처럼 보였다. 크기가 다른 뷰포트 두 개 이상에서
  같은 문서를 비교하는 것이 가장 빠른 판별법이었다.
- **"컴포넌트 기본 크기 + 호출부 style" 병합 패턴은 width만 덮는 호출부와 만나면 위험하다.** 렌더 결과의 스타일을
  `StyleSheet.flatten`으로 단언하는 테스트를 두면 같은 실수를 CI가 잡는다. 다만 리뷰 봇 지적대로 이번 회귀 테스트는
  `Room`에만 추가했고, 꾸미기 화면 쪽 단언은 아직 없다.
- **뷰가 맞아도 데이터가 옛것이면 불일치다.** 편집 결과를 저장하는 경로에는 그 문서를 그리는 모든 캐시(썸네일 포함)의
  무효화를 함께 둔다(#1027 react-query 이관 규칙과 같은 문제의식).
- 공통 계약에는 모든 뷰포트가 공유하는 값만 둔다. 한 화면만의 예외를 계약에 넣으면 나머지 뷰포트가 함께 바뀐다(#1191 → #1193).
- 관련 사례: 집 화면에서 개인 방을 합성하는 규칙은
  [서로 다른 개인 방을 한 집에 자연스럽게 보여주기](2026-11-04-shared-house-diorama.md)에 따로 정리했다.
  거기서는 개인 방 좌표를 재사용하지 않고 장면별 규칙을 새로 정의했다.
