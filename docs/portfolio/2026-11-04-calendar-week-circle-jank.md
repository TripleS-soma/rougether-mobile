# 달력 날짜를 누르면 원이 튀고 버벅이던 문제 — 늦게 오는 onLayout과 JS 스레드 경합

- 2026-11-04 / routine-todo(달력) / 이슈 #1601, PR #1602 (주간 보기 #1327, 선택 원 슬라이드 #452)
- 키워드: React Native UI 스레드 vs JS 스레드, Reanimated useAnimatedStyle, onLayout 지연, 스프링 감쇠, requestAnimationFrame 실측

## 배경

달력 탭에서 날짜를 누르면 같은 자리의 달력이 그 주 한 줄로 접히는 "주간 보기"로 바뀐다(#1327). 선택 날짜에는 떠 있는 원 하나가 날짜 사이를 미끄러져 다닌다(#452). 원의 좌표는 각 날짜 칸이 `onLayout`으로 보고한 실측 위치를 쓴다.

## 문제 (증상)

사용자 제보: 날짜를 누르면 원이 튀거나, 바로 제자리를 찾지 못하고 흔들리다 찾아가며, 화면이 버벅인다.

## 원인 분석 (가설 → 검증 과정)

날짜 한 번 탭에 네 가지가 겹친다는 것을 코드로 추적했다.

1. 주간 보기는 화면 전환 없이 **방 화면 인스턴스를 하나 더 마운트**한다 — 첫 프레임들 JS 스레드가 바쁘다.
2. 같은 순간 줄 접힘과 "주간 보기" 헤더가 **둘 다 height 애니메이션**이었다. height는 RN `Animated`의 네이티브 드라이버가 못 다뤄 JS 드라이버로 돌았고, 1과 같은 스레드를 다퉜다.
3. 원은 접히는 줄을 직접 따라가지 않고, **줄 `onLayout` 이벤트가 올 때마다 `setValue`로 순간이동**했다. 이벤트는 프레임보다 늦고 띄엄띄엄 와서, 원이 움직이는 칸을 계단식으로 뒤쫓았다. 마운트 직후엔 줄 높이 실측 → 재렌더를 거쳐야 접힘이 시작돼 원이 월 보기 자리에 먼저 찍혔다.
4. 가설 하나 더 — 스프링 자체가 출렁인다. 웹(휴대폰 폭 iframe)에서 날짜를 누른 뒤 `requestAnimationFrame`마다 "원 중심 − 목표 칸 중심" 거리를 기록했다: **−192px → +25px(지나침) → 0**, 정착까지 약 350ms. friction 7·tension 90 스프링이 목표를 지나쳤다 돌아오는 것이 주간 보기 안에서 요일을 바꿀 때의 "튐"이었다.

주간 보기 진입은 웹에서 꺼져 있어(`onOpenDay` 네이티브 전용) 1~3은 웹으로 재현하지 못했다 — 코드 추적 기반이다.

## 해결

- **움직이는 동안엔 원 대신 칸을 칠한다.** 접힘·펼침이 진행 중(`foldSettled=false`)이면 떠 있는 원을 숨기고 선택 칸 배경을 칠한다. 칸은 줄과 같은 프레임에 움직이니 어긋날 수 없다. 멈추면 원을 최종 칸에 한 번 얹고 되돌린다 — 같은 주 안의 요일 슬라이드는 살린다. 움직이는 동안엔 `onLayout`으로 원을 쫓지 않는다.
- **height 애니메이션을 UI 스레드로.** 줄 접힘(`FoldRow`)과 헤더를 Reanimated `useAnimatedStyle` + `withTiming`으로 바꿨다. 같은 220ms·같은 out-cubic 곡선. JS가 마운트로 바빠도 애니메이션 프레임은 UI 스레드가 그린다.
- **스프링을 임계 감쇠로.** `bounciness: 0, speed: 18`.

## 결과 (수치)

- 웹 rAF 실측(원 중심 − 칸 중심, 세로): 전 −192 → **+25 지나침** → 0, 약 350ms / 후 +128 → 0 **단조 감소(지나침 0)**, 약 340ms 정착.
- 테스트 2개 추가(접히는 동안 선택 칸 채움, 월 보기는 채우지 않음). 전체 414 스위트 · 3445 통과.
- 주간 보기 진입 시의 체감 개선은 실기기 확인 대기.

## 배운 점 / 재발 방지

- **위치를 이벤트로 쫓지 말고, 같은 프레임에 움직이는 것에 붙여라.** `onLayout`은 "다 끝난 뒤의 측정"이지 애니메이션 프레임 신호가 아니다.
- height·width처럼 레이아웃 속성을 움직이는 애니메이션은 RN `Animated`에선 JS 드라이버로만 돈다 — 무거운 마운트와 겹치는 자리면 Reanimated로.
- "튄다"는 제보는 스프링 설정부터 rAF로 재 보면 빠르다. 숫자 하나(지나침 px)로 가설이 갈린다.

## 후속 (2026-11-04) — 주간 보기에서 나올 때 달력이 깜빡임, 그리고 측정법의 함정

**증상**: 주간 보기에서 뒤로 나오면 달력 화면이 깜빡였다(사용자 제보). 접히는 동안의 버벅임 제보도 이어졌다.

**측정부터 다시**: 처음엔 Android 에뮬레이터 + 개발 번들로 rAF 간격과 React Profiler를 쟀는데, 같은 조작이 실행마다 수백 ms씩 흔들려 고친 전후를 가를 수 없었다(개발 번들은 운영보다 몇 배 느리고, 에뮬레이터는 소프트웨어 GPU). 로컬 **릴리스 APK**(디버그 키 서명이라 개발 설치본 위에 덮어 설치해 로그인 유지)로 바꾸고, 같은 조건을 A/B로 번갈아 쟀다. 그래도 진입 수치는 에뮬레이터 상태에 따라 갈렸다(막 켠 직후 A 83~~89프레임/1.5s, 30분 뒤 A 22~~45프레임) — **같은 시점에 기준(A)을 다시 재지 않으면 "개선"이 착시**였다. 반대로 깜빡임은 `adb screenrecord` → `ffmpeg fps=20,tile=8x5` 프레임 모음으로 눈에 보이는 결함이라 판정이 흔들리지 않았다.

**원인 (녹화로 확인)**

1. 주간 보기는 탭이 없는 화면이라 셸이 탭 페이저를 언마운트했다가, 돌아오면 다시 마운트한다. 페이저는 폭을 `useState(0)`으로 시작해 첫 프레임에 페이지 폭이 없어 글자가 세로로 꺾였고("Al l", "Ro ut in e"), `onLayout` 전까지 빈 화면이 3~5프레임 나왔다.
2. 다시 마운트된 달력은 선택 원을 "첫 등장"으로 보고 0→1로 140ms 페이드했다.
3. #1602의 "접히는 동안 선택 칸 채움"이 Android에서 **네모**로 그려졌다 — 배경 없던 뷰에 배경만 덧칠하면 Fabric이 평탄화했던 뷰를 되살리며 `borderRadius`를 잃는 것으로 보인다(녹화 실측, 원인 추정).

**해결**: 페이저가 앱 프레임 폭과 현재 탭 위치(`tx = -index × width`)로 시작(실제 폭은 `onLayout`이 보정), 마운트 직후 첫 배치는 페이드 없이, 선택 칸 채움은 기존 뷰 덧칠 대신 둥근 모서리+배경을 처음부터 가진 별도 뷰로.

**버린 후보**: 주간 보기 동안 페이저를 숨긴 채 유지(`display:none`)는 깜빡임을 없앴지만, 같은 조건 재측정에서 진입 개선을 보이지 못했고 숨은 다섯 탭이 셸 리렌더를 계속 받는다. 목록 렌더를 접힘 뒤로 미루는 안도 같은 이유로 보류.

**결과**: 릴리스 빌드 복귀 녹화 — 찌그러진 프레임 2개·빈 프레임 5개(A) → 0개, 네모 채움 → 둥근 채움. 펼침 ~0.5s 동안 선택 표시가 비는 구간은 A에도 있던 것으로 남음.

**배운 점**: 성능 숫자는 개발 번들·에뮬레이터에선 방향만 본다. 비교는 같은 세션에서 기준을 다시 재는 A/B로, 눈에 보이는 결함은 숫자보다 녹화 프레임으로.

## 후속 2 (2026-11-04) — 실기기 영상이 원인을 확정, 새 화면 대신 제자리 전환

**증거**: 사용자 Android 실기기(릴리스) 화면 녹화 30fps를 프레임으로 펼치자, 날짜를 누른 뒤 **약 9프레임(300ms) 동안 화면이 얼었다가** 접힘이 3~4프레임에 몰아쳤다. 에뮬레이터 수치로는 끝내 갈리지 않던 것이 한 장면으로 확정됐다.

**원인**: 주간 보기가 "탭 없는 별도 화면"이라, 날짜를 누르면 셸이 다섯 탭 페이저를 언마운트하고 `MyRoomScreen`을 하나 더 마운트했다. 그 마운트가 JS를 막는 동안 줄 높이 실측 → 재렌더(접힘 시작 조건)도 밀려, 헤더만 자라고 줄은 늦게 한꺼번에 접혔다.

**해결**: 주간 보기를 페이저의 달력 페이지가 **제자리에서** 바뀌는 모드로. 셸은 `calendarWeek` 화면에서도 페이저를 그대로 두고 달력 페이지에 주간 props만 넘긴다(같은 자리·같은 컴포넌트라 React가 새로 만들지 않음). 주간 동안 페이저 스와이프를 잠가 주 넘기기와 다투지 않게, 화면이 살아 있으니 월로 돌아오면 `weekLeaving`을 푼다. 내비게이션 상태(`calendarWeek` 화면·뒤로·엣지 백)는 그대로라 흐름 변경은 셸과 잠금 훅 두 곳.

**결과 (에뮬레이터 릴리스 녹화, 같은 세션 A/E)**: 탭 → 접힘 시작 약 12프레임(400ms) → 약 5프레임(160ms), 접힘이 한 번에 넘어가지 않고 4~5프레임에 걸쳐 진행. 복귀 시 꺾인 화면·네모 채움 0.

**배운 점**: "새 화면을 띄우는 연출"은 그 화면의 마운트 비용을 애니메이션 첫 프레임에 고스란히 얹는다. 같은 데이터를 보는 화면이면 모드 전환으로 — 측정이 흔들릴 땐 실기기 녹화 한 편이 가장 강한 증거다.

## 후속 3 (2026-11-06) — 돌아가는 길: 로그는 켜졌다는데 화면엔 없는 칸 채움

**증상**: 주간 보기에서 뒤로를 누르면 달력 탭으로 돌아오는 전환이 버벅인다는 제보. 후속 2가 들어가는 길을 고쳤다면 이번엔 나가는 길이다.

**측정**: 로컬 릴리스 APK를 로그인된 설치본 위에 덮어 깔고, `screenrecord` 프레임을 **타임스탬프째 전수**로 펼쳤다(에뮬레이터는 화면이 바뀔 때만 프레임을 내서 균일 샘플링하면 같은 장면이 반복된다). 세 결함이 한 녹화에 다 보였다 — ① 선택 날짜의 원이 약 4프레임 사라졌다 돌아옴 ② 주간 목록이 펼침 내내 남았다가 마지막에 한 프레임에 사라짐 ③ 끝에서 달력 전체가 약 16dp 위로 튐.

**가설 → 검증**: ①은 "펼치는 동안엔 떠 있는 원 대신 칸을 칠한다"는 기존 설계가 있는데도 비었다. 렌더마다 상태를 `console.warn`으로 찍어 릴리스 logcat으로 읽자 두 가지가 드러났다.
- 뒤로 첫 렌더(`weekOf=null`)에 접힘 상태가 **아직 '멈춤'**이었다. 불리언이라 "어느 방향으로 멈췄는지"를 몰라, 펼침이 시작되는 렌더에 옛 자리 원이 남았다.
- 그다음 렌더부터는 로그상 `fill: true`인데 **녹화엔 빈 칸**이었다. 펼침이 시작되는 순간 칸 채움 뷰를 새로 마운트하면 Android가 움직이는 동안 그 뷰를 그리지 않았다.

③은 수치로 바로 풀렸다. 헤더는 높이만 0으로 접히고, 부모의 `gap` 16은 남아 있다가 화면이 월 모드로 바뀌는 순간 사라졌다.

**해결**:
- 접힘 상태를 방향별로 든다(`settledFor === collapsed`). 이제 첫 렌더부터 칸 채움이 켜진다.
- 칸 채움 뷰는 늘 마운트해 두고 `opacity`만 0/1로 바꾼다.
- 헤더의 `marginBottom`을 `(weekIn − 1) × gap`으로 두어 간격도 같은 애니메이션 값으로 접는다.
- 목록도 같은 값으로 페이드한다.

**결과 (같은 에뮬레이터 세션 A/B 녹화)**:
- 원이 비는 프레임: 4 → 0
- 끝의 튐: 약 16dp → 0. 헤더가 줄어드는 동안 달력이 함께 올라가 마지막 프레임과 위치가 같다.
- 목록: 한 프레임에 사라지던 것이 220ms 동안 걷힌다.

**배운 점**: 로그는 "렌더가 무엇을 요청했나"이고 녹화는 "화면이 무엇을 그렸나"다. 둘이 어긋나는 지점이 플랫폼 결함이 사는 곳이다. 그리고 레이아웃 애니메이션은 높이만이 아니라 그 요소가 부모에게서 받는 간격(gap·margin)까지 함께 접어야 끝에서 튀지 않는다.
