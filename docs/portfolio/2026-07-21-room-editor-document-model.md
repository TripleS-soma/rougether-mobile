# 방 꾸미기 에디터의 문서 모델 — 해상도와 무관한 좌표, 리비전으로 막는 저장 충돌

- 2026-07-21 / room / #327 (PR #332), 후속 #333 (PR #334), #925 (PR #931)
- 키워드: 문서 모델, 해상도 독립 정규화 좌표(0~1), 낙관적 동시성 제어(revision·409), 전체 교체 저장, 더티 체크(스냅샷 비교), 렌더 계약

## 배경

방 꾸미기는 원래 **슬롯 방식**이었다. 방에 정해진 칸(좌상단·가운데 등)이 있고, 가구는 그 칸 중 하나에만 들어갔다.
2026-07-20 스웨거에서 서버의 자유 배치 API를 발견했다. 그래서 방 꾸미기를 캔버스 에디터처럼 바꾸기로 했다. 가구를
끌어서 아무 데나 놓고, 회전·반전·크기·앞뒤 순서를 바꿀 수 있게 한다(FREE_V1).

이 전환은 화면을 새로 만드는 일보다 **저장되는 문서를 어떻게 정의하느냐**의 문제가 더 컸다. 같은 방이 크기가 서로 다른
여러 화면에 그려지기 때문이다.

- 나의 방(전체 폭)
- 친구 방
- 집 화면의 작은 미리보기 타일
- 웹(PWA)
- 관리자 도구

한 사용자가 폰과 웹에서 같은 방을 동시에 열 수도 있다.

## 문제 (증상)

에디터의 저장 모델이 답해야 할 질문은 세 가지였다.

1. **좌표를 무엇으로 저장하나.** 화면 픽셀로 저장하면 기기마다 가구 위치가 달라진다. 큰 화면에서 놓은 가구가 작은
   미리보기 타일에서는 방 밖으로 나간다.
2. **두 기기가 동시에 편집하면 어떻게 되나.** 배치는 전체 교체로 저장된다. 나중에 저장한 기기가 먼저 저장한 기기의
   편집을 조용히 덮어쓰게 된다(lost update).
3. **"저장 안 한 변경이 있다"를 어떻게 판단하나.** 드래그·회전·크기 조절이 모두 같은 상태를 바꾼다. 나가기 전에
   물어볼지 정하려면 변경 여부를 믿을 수 있게 판정해야 한다.

## 원인 분석 (가설 → 검증 과정)

**좌표.** 서버 계약(spec `domains/room/api.md`)은 위치를 **방 렌더 영역 기준 0.0~1.0 정규화 좌표**로 정했다.
`positionX/Y`, `zIndex`, `scale`, `rotationDeg`, `flipped`를 함께 저장한다. 그래서 클라이언트 쪽 질문은 "정규화 좌표를
화면마다 같은 모습으로 되살리려면 무엇을 고정해야 하나"로 바뀌었다. 방의 가로세로 비율이 화면마다 다르면 같은 (x, y)라도
모습이 달라진다. 가구 크기도 가로 기준인지 세로 기준인지 정해야 한다. 이 값들을 컴포넌트 여기저기에 매직 넘버로 두면 표면마다
조금씩 어긋날 위험이 있었다.

**동시 편집.** 서버는 방에 `layoutRevision`을 두고 저장 요청의 `baseRevision`과 비교한다. 두 값이 다르면
409 `ROOM_LAYOUT_REVISION_CONFLICT`를 돌려준다. 잠금 없이 "내가 읽은 버전 위에서만 쓸 수 있다"는 **낙관적 동시성 제어**다.
머지 전에 일회용 dev 계정으로 실서버에서 계약을 직접 확인했다(PR #332 본문).

- 첫 저장을 하면 방이 `FREE_V1`로 바뀌고 리비전이 1이 된다.
- 낡은 `baseRevision`으로 저장하면 409 `REVISION_CONFLICT`가 돌아온다.

남은 질문은 409를 받았을 때 클라이언트가 무엇을 할지였다.

**전환의 비가역성.** 첫 FREE_V1 저장은 되돌릴 수 없다. 그 뒤로는 구 슬롯 저장 API가 409
`ROOM_LAYOUT_FORMAT_CONFLICT`를 낸다. 그래서 공용 dev 계정(계정 4)은 머지 전에 일부러 전환하지 않았다. 머지 전에 dev 계정이
FREE_V1이 되면 구버전 앱의 슬롯 저장이 깨지기 때문이다.

## 해결

**1. 문서 = 정규화 좌표 배열, 화면 = 그 문서의 투영.**

- 앱 내부 모델 `PlacedFurniture { furnitureId, x, y, z, scale, rotationDeg, flipped }`를 서버 필드와 1:1로 맞췄다.
  `src/api/adapters/room.ts`의 두 함수가 경계를 맡는다.
  - `fromRoomPlacements`: 서버 → 앱. 보유 아이템 id로 찾고, 없으면 assetKey로 찾는다. 카탈로그에 없는 가구는 건너뛴다.
  - `toLayoutPlacements`: 앱 → 서버. 보낼 때 0~1로 클램프한다.
- 렌더러는 좌표를 픽셀로 바꾸지 않는다. `left/top`을 **퍼센트 문자열**(`roomPercent`)로 넘긴다. 그래서 같은 문서를
  나의 방·친구 방·집 미리보기 타일이 같은 코드로 그린다.
- 화면마다 다를 수 있는 기하 상수는 **렌더 계약 JSON 한 곳**(`room-render-contract.v2.json`, 2026-07-22 도입)에 모았다. 이 계약을 여러 화면이 각자 다르게 적용해 생긴 문제와 해결은 [같은 방이 화면마다 다르게 보이던 문제](2026-09-08-room-render-contract.md)에 따로 적었다.
  - 방 비율 `aspectRatio` 0.8333
  - 가구 기준 폭 `baseWidth` 0.28
  - 중심 앵커 `furnitureAnchor: center`
  - 새 가구 위치 `newPlacementCenter` (0.5, 0.55)
  - 편집 배율 범위 `editorScale` 0.5~3.5

  드래그 경계 클램프(`furnitureClampBounds`)도 이 값에서 계산한다. 정사각형 가구의 세로 반경은 가로 반경에 방 비율을
  곱해 구한다. 관리자 도구는 같은 버전의 JSON을 그대로 가져다 쓴다(vendoring). 그래서 앱과 도구가 같은 기하를 쓴다.

**2. 저장 = 전체 교체 + baseRevision, 결과는 세 갈래.**

- `useShop().saveLayout`(`src/hooks/use-shop.ts`)이 최신 `layoutRevision`을 `baseRevision`으로 실어 `PUT /rooms/me/layout`을
  보낸다. 결과는 `'ok' | 'conflict' | 'fail'` 세 가지로 돌려준다.
  - `ok`: 보낸 본문과 새 리비전을 react-query 캐시에 바로 쓴다. 다시 조회하지 않아도 나의 방이 저장한 모습이 된다.
  - `conflict`(409 REVISION_CONFLICT): 토스트 없이 화면에 맡긴다. 이 409는 예상한 상태이므로 `expectedStatuses: [409]`로
    에러 집계에서도 뺐다.
  - `fail`: 실패 토스트만 띄운다.
- 충돌이 나면 꾸미기 화면이 "다른 기기에서 먼저 저장했어요" 모달을 띄운다. "새로 불러오기"를 누르면 서버 상태를 다시 받고
  화면을 나간다. **자동 병합은 하지 않았다.** 배치는 전체 교체라서 두 편집본을 섞을 기준이 없다. 섞은 결과는 사용자가 어느
  기기에서도 본 적 없는 방이 된다. 그래서 "지금 편집은 사라진다"고 정직하게 알리고, 서버 쪽을 정본으로 삼았다.

**3. 더티 체크 = 저장 시점 스냅샷과의 문자열 비교.**

- 꾸미기 화면은 `snap(items, wallpaper, floor, background)`로 문서 전체를 직렬화한다. 마운트 시점과 마지막 저장 성공 시점의
  스냅샷을 ref에 들고, 현재 스냅샷과 비교해 `dirty`를 판정한다. 좌표까지 비교하므로 가구를 조금만 옮겨도 "저장할까요?"가
  뜬다. 충돌이나 실패로 끝난 저장은 기준 스냅샷을 갱신하지 않는다. 그래서 dirty가 그대로 남는다.
- 후속 성능 정리(PR #772)에서 이 직렬화를 `useMemo`로 감쌌다. 이때 **비싼 직렬화만 memo하고, 기준 ref와의 비교는 매 렌더**
  하도록 나눴다. 기준 스냅샷은 ref 변경이라 memo 의존성에 잡히지 않는다. `dirty` 전체를 memo했다면 저장 직후에도 낡은
  `true`가 남아 "변경사항을 저장할까요?"가 잘못 다시 떴을 것이다. 리뷰에서 이 함정을 짚었다. 기존 테스트 "저장 후 dirty
  해제"가 이 경우를 덮고 있다.

**4. 단계적 전환.** 1차(PR #332)는 이동·빼기·저장, 2차(PR #334)는 선택 링·회전·반전·z 순서·크기 조절로 나눴다. 2차는
편집 UI만 추가했다. `scale/rotationDeg/flipped`는 1차부터 저장 페이로드와 렌더러에 이미 들어 있었다. 그래서 서버 변경 없이
도구만 늘릴 수 있었다. 마지막으로 PR #931(2026-08-20)에서 슬롯 렌더 폴백을 전부 걷어냈다. 이제 가구의 정본은 `placements`
하나다. 걷어내기 전에 실서버 표본 4개 방이 전부 FREE_V1인지 확인했다. 첫 스토어 빌드(2026-08-02)에는 슬롯 쓰기 코드가
이미 없었다는 이력도 확인했다.

  `placements` 하나로 정상 렌더되는 것을 확인했다.

## 배운 점 / 재발 방지

- **에디터는 문서 모델부터 정한다.** 좌표계·원점·앵커·비율을 계약 파일 하나에 두면, 렌더 표면이 늘어도 "어느 화면 기준
  좌표냐"는 질문이 다시 생기지 않는다. 픽셀 변환은 렌더 직전 한 곳(퍼센트 배치)에서만 한다.
- **전체 교체 저장에는 리비전이 짝이다.** 리비전 없이 전체 교체를 하면 마지막 저장이 조용히 이긴다. 409를 "에러"가 아니라
  예상한 결과 값(`'conflict'`)으로 모델링하면, UI가 그 갈래를 빠뜨리지 않고 다루게 된다.
- **ref에 든 기준값은 memo가 보지 못한다.** 더티 판정처럼 "비싼 계산 + 바뀌는 기준"이 섞이면 계산만 memo하고 비교는 매 렌더
  한다.
- 남은 한계(관찰, 미검증): 서버는 `positionX/Y`를 소수 5자리, `scale`을 소수 2자리로 반올림해 저장한다(spec). 그런데 저장
  성공 시 캐시에는 응답이 아니라 **보낸 본문**을 쓴다. 다음 조회 전까지 캐시와 서버 값이 반올림 오차만큼 다를 수 있다.
  눈에 보이는 차이는 없을 것으로 추측하지만 측정하지는 않았다.
