## 릴리스·배포 인프라 (2026.08 ~ 2026.11)

**과정**

- Expo(React Native) 앱을 EAS Build로 빌드해 TestFlight와 스토어에 올리고, JS 변경은 스토어를 거치지 않는 OTA(EAS Update, 앱 재설치 없이 JS만 배포하는 방식)로 배포했다.
- `runtimeVersion` 정책을 `fingerprint`로 두었다. 네이티브에 영향을 주는 파일의 해시(이하 런타임 지문)가 런타임 버전이 되고, OTA는 같은 지문의 바이너리에만 도달한다.
- 개발용 OTA 경로와 스토어용 OTA 경로(이하 레인)를 채널로 나눠 운영했다. 개발 레인은 dev 브랜치 머지마다 자동 발행하고, 스토어 레인은 main 승격 후 수동 발행한다.
- 네이티브 SDK를 붙일 때마다 EAS 클라우드 빌드 쿼터와 심사 일정이 걸려 있어, 빌드 산출물 검사와 로컬 Release 검증을 앞단에 두었다.

### 테스트·빌드·업로드를 모두 통과한 iOS 빌드가 켜자마자 종료됨 (2026.08)

**문제**

- iOS 1.2.0(빌드 47)이 TestFlight에서 스플래시만 보이고 즉시 종료됐다. 같은 빌드가 EAS 빌드, CI(테스트 990개), App Store Connect 업로드를 모두 통과한 상태였다.
- 크래시 로그는 잡히지 않은 Objective-C 예외였고 Sentry에는 아무것도 남지 않았다.

**원인**

- 정상이던 빌드 43과 빌드 47의 IPA 번들을 통째로 비교해, 차이가 버전 문자열, 빌드 번호, `Info.plist`에서 `NSRemindersUsageDescription` 계열 키 두 개가 사라진 것뿐임을 확인했다.
- 캘린더 읽기 전용을 위해 만든 config plugin이 `expo prebuild` 때 이 키를 지웠고, `expo-calendar`는 앱 시작 시 키가 없으면 `RCTFatal`을 호출했다. 테스트는 입력인 `app.json`만 봐서 이를 놓쳤다.

**해결**

- 플러그인을 고쳐 미리알림 키와 Android `WRITE_CALENDAR`를 복구했다(#914). 권한 선언은 넓어지지만 동작은 읽기 전용 그대로다.
- CI에서 `expo prebuild --no-install` 후 생성된 `Info.plist`의 필수 키를 검사하는 산출물 가드를 추가했다(#933). 싸고 치명적인 검사라 라벨 조건 없이 모든 PR에서 돌린다.
- Android는 금지 권한에 제거 지시자(`tools:node="remove"`)가 붙어 있는지와 병합 매니페스트의 필수 권한을 검사하도록 확장했다.

### prebuild 생성물이 런타임 지문을 갈라 iOS 빌드가 실패함 (2026.09)

**문제**

- 1.5.3 iOS 빌드 124가 `Configure expo-updates` 단계에서 `Runtime version mismatch`로 실패했다. CI 러너가 계산한 값(`0ed984cc…`)과 EAS 워커가 계산한 값(`8ae89c49…`)이 달랐고, 같은 커밋의 Android 빌드는 정상이었다.
- 실패한 빌드도 EAS 쿼터를 소모한다.

**원인**

- 과거 원인(심링크 `node_modules`, `npm ci` 누락)은 CI 러너가 `npm ci` 후 계산했으므로 배제하고, EAS 로그를 풀어 지문 diff를 읽었다. 차이는 `targets` 디렉터리 해시 하나였다.
- 로컬에서 `expo prebuild --platform ios`를 돌리면 `targets/widgets/Assets.xcassets/`가 생기고, 그 상태의 지문이 정확히 EAS 값과 같았다. 러너는 prebuild 전, EAS는 prebuild 후의 파일을 해싱하고 있었다.

**해결**

- `.fingerprintignore`에 생성물 경로 `targets/**/Assets.xcassets/**`만 추가했다. 원본 이미지 경로는 `expo-target.config.js`에 있어 지문에 계속 포함되므로 위젯 이미지를 바꾸면 지문도 바뀐다.
- 규칙 추가 후 iOS 지문이 생성물 유무와 무관하게 같음을 확인하고 머지했으며, 재빌드는 한 번만 올렸다(빌드 125 성공).

→ [사례 기록](2026-09-16-fingerprint-prebuild-artifact.md)

### 심사에 제출된 테스트 빌드가 개발 OTA를 받음 (2026.09)

**문제**

- 1.5.3 iOS를 심사에 올리면서 스토어용 production 빌드 대신 채널 `dev`의 TestFlight 빌드 125가 제출됐다.
- 그대로 두면 dev 머지마다 심사 중인 바이너리가 새 JS를 받아 제출본과 코드가 달라지고, 출시 후에는 스토어 사용자가 검증 안 된 개발 코드를 받는다. 확인 시점에 대기 중인 JS 변경 PR도 있었다.

**원인**

- App Store Connect의 "빌드 추가" 목록에서 TestFlight 빌드와 production 빌드가 구분되지 않아 생긴 제출 실수였다(과거 1.4.0 빌드 111에서도 같은 일이 있었다).
- 바이너리 교체는 재빌드와 재제출이 필요하지만, 채널이 어느 브랜치를 받을지는 서버 설정이라 즉시 바꿀 수 있다는 점에 착안했다.

**해결**

- 바이너리는 두고 채널 매핑만 바꿨다. `dev` 채널을 `production` 브랜치로 돌리고, 새 `internal` 채널을 `dev` 브랜치에 연결한 뒤 `eas.json`의 `testflight`·`preview` 프로필 채널을 `internal`로 교체했다(#1373). `eas.json`은 지문 입력이 아니어서 기존 설치본의 OTA가 끊기지 않는다.
- 대기 중이던 PR을 드래프트로 되돌려 재배선 전에는 머지되지 않게 하고, 확인 후에 머지했다.

→ [사례 기록](2026-09-16-ota-channel-remap.md)

### 네이티브 지문이 바뀐 뒤 OTA 레인에서 이탈한 설치본에 업데이트 안내하기 (2026.10)

**문제**

- 네이티브 지문이 바뀌면 이전 바이너리는 OTA를 영구히 받지 못한다. 1.5.3 설치본이 이렇게 남아 피드와 거래소 기능 없이 고정됐는데, 앱에는 스토어 업데이트를 알릴 수단이 없었다.
- 이 안내 기능도 OTA로 전달되므로 새 네이티브 모듈을 추가하면 지문이 바뀌어 현재 설치본(1.5.4)에도 닿지 않는다.

**원인**

- JS만으로 설치된 바이너리를 식별할 방법을 세 후보로 검증했다. `Constants.expoConfig.version`은 OTA 번들의 값이라 탈락했다.
- `Constants.platform.android.versionCode`는 타입에는 있지만 `expo-constants`의 `ConstantsService.kt`를 읽어 보니 빈 객체여서, Android에서 아무 로그 없이 동작하지 않을 상황이었다(코드 리뷰 지적으로 발견). `expo-application`은 네이티브 모듈이라 지문이 바뀐다.
- 남은 `Updates.runtimeVersion`은 같은 레포의 `release-channel.ts`가 이미 쓰던 방식이었다.

**해결**

- `Updates.runtimeVersion`을 랜딩의 `app-version.json`과 대조하는 버전 게이트를 만들었다(#1573). 랜딩은 main 푸시가 즉시 배포라 앱 배포 없이 게이트를 켜고 끌 수 있다.
- 목록은 최신 지문이 아니라 오래된 지문을 나열하게 했다. 사람이 잊었을 때 최신 사용자를 조르는 대신 아무 일도 일어나지 않게 하려는 선택이다. 설정 없음, 조회 실패, 지문 미확인은 모두 통과시킨다.
- 원격 JSON에는 스토어 주소를 두지 않고 앱 상수가 정하게 했다. 화면을 막을 때도 내비게이터를 내리지 않고 접근성 트리에서만 걷어 냈다.

**추가적인 문제**

- 이슈에 적은 "1.5.3 이하 설치본은 구제 불가"는 틀렸다. `hotfix-ota` 워크플로가 `expected_runtime`으로 특정 런타임을 조준해 발행할 수 있어, 1.5.3 커밋에서 분기해 이 변경만 얹으면 닿는다. 정상 레인에서 검증한 뒤 할 일로 남겼다.
- 게이트는 아직 꺼진 상태(목록이 비어 있음)이며, 다음 네이티브 릴리스 때 직전 빌드 지문을 `staleRuntimes`에 넣으면 동작한다.

→ [사례 기록](2026-10-25-ota-stranded-install-version-gate.md)

### Meta SDK를 넣자 iOS Release 링크가 깨짐 (2026.11)

**문제**

- 앱 설치 광고 측정을 위해 `react-native-fbsdk-next` 13.4.3을 붙이자, `pod install`까지는 통과하지만 Release 시뮬레이터 빌드가 링크 단계에서 `Undefined symbols`(`RCTConvert`, `RCTRegisterModule` 등)로 실패했다.
- 컴파일은 모두 통과했다.

**원인**

- 미정의 심볼이 아키텍처 문제로는 설명되지 않았다. FBSDK가 아니라 React 자신의 심볼이었고 다른 pod는 멀쩡했기 때문이다.
- 실패한 링크 명령에는 `-F …/React-Core-prebuilt` 검색 경로는 있었지만 `-framework React`가 없었다. 정상 pod는 podspec에서 `install_modules_dependencies`를 부르는데, 이 라이브러리는 옛 방식의 `s.dependency 'React-Core'`만 선언했다. dynamic framework는 pod마다 독립적으로 링크되어 그 시점에 React가 없으면 바로 실패한다.

**해결**

- 라이브러리를 포크하지 않고 config plugin(`plugins/with-fbsdk-react-link.js`)으로 Podfile `post_install`에 블록을 주입해 해당 타깃의 `OTHER_LDFLAGS`에만 `-framework React`를 붙였다(#1623). `ios/`는 prebuild마다 새로 생성되므로 플러그인이 유일한 지속 경로다.
- Ruby로 `post_install` 블록을 실제 실행하는 단위 테스트로 기존 플래그 보존, 다른 pod 불변, 반복 prebuild 시 중복 없음을 고정했다.

→ [사례 기록](2026-11-04-fbsdk-prebuilt-rn-link-failure.md)

### 공식 SDK 다운로드 장애와 네이티브 지문 추적 누락 (2026.11)

**문제**

- 새 iOS 후보의 Release 검증에서 CocoaPods가 FBAEMKit 18.1.1을 설치하지 못했다. Facebook SDK의 공식 GitHub release 다운로드 URL이 HTTP 504를 반환했고, 같은 job을 다시 실행해도 같았다.
- 확인한 것은 빌드 준비 단계의 장애이며, 운영 사용자 앱이 같은 원인으로 고장 났다고 확인한 것은 아니다.

**원인**

- 실패 위치가 컴파일 이전의 단일 archive 전송이어서 앱 코드나 버전 충돌이 아님을 구분했다. 원래 URL은 실패했지만 공식 GitHub asset API는 같은 공개 archive를 정상 반환했다.
- 공식 metadata의 크기와 SHA256을 실제 다운로드와 대조해 같은 파일임을 확인했다.
- 별도 Ruby loader를 만든 뒤에는 기본 지문 수집기가 Podfile에서 나중에 읽는 Ruby 파일을 추적하지 않음도 확인했다. 그대로면 Ruby 파일만 바꿔도 지문과 실제 네이티브 입력이 어긋날 수 있었다.

**해결**

- 정확한 v18.1.1 URL에만 반응하는 작은 adapter를 기존 iOS config plugin에 연결해, 공식 asset API와 공식 SHA256을 CocoaPods downloader에 넘겼다. SDK 버전과 링크 설정은 바꾸지 않았고 다운로드와 체크섬 검사는 기존 구현을 썼다.
- 실제 `cocoapods-downloader` 2.1에서 네트워크 부분만 대체한 테스트로 잘못된 체크섬을 거절하는지 확인했다. `fingerprint.config.js`의 `extraSources`에 Ruby 파일을 추가하고, 주석 한 줄만 넣어도 지문이 달라지는지 측정했다.

### OTA 발행 성공 후에도 스토어 iOS 설치본에 기능이 없음 (2026.11)

**문제**

- 게시물 상세의 입주 신청 버튼이 스토어 iOS 앱에 없다는 제보가 왔다. 앞서 배포 완료라고 안내했지만 실제 스토어 설치본에 닿았는지는 충분히 확인하지 않은 판단이었다.

**원인**

- 서버 health와 신규 API 경로는 정상이었다. 기존 iOS OTA의 대상 런타임은 `05075342…`였지만 스토어용 후속 OTA의 대상은 `05f36fe5…`였다.
- 스토어 대상 소스 `c8050972…`의 트리를 확인하자 입주 API 파일과 버튼 배선이 없었다. 런타임이 맞는 발행이 없었으므로 재실행으로는 해결되지 않았다.

**해결**

- 스토어 런타임의 최신 소스에서 분기해 입주 기능의 `src` 변경만 3-way로 이식했다. 네이티브 설정은 그대로 두고 지문이 `05f36fe5…`와 일치함을 확인한 뒤 정식 `hotfix-ota` 워크플로로 발행했다.
- 기능은 dev와 main에 이미 있어 중복 기능 PR은 만들지 않았다.

**추가적인 문제**

- production 업데이트 서버가 스토어 런타임 요청에 HTTP 200과 update ID를 준 것까지만 확인했고, 사용자 기기의 실제 다운로드와 실행은 직접 확인하지 못했다.

→ [사례 기록](2026-11-11-ios-store-ota-feature-gap.md)

**최종 성과**

산출물 검사는 iOS 필수 키 7개와 금지 1개, Android 권한 규칙 15개와 병합 필수 2개 등으로 늘었고, 반복 사용하던 스크립트 3개는 오픈소스 CLI `expo-release-guard`(테스트 82개)로 옮겼다. 지문 불일치는 실패 1회 이후 재빌드 1회(빌드 125)로 해결했고, 채널 재배선은 재빌드와 재제출 0회로 심사 빌드를 스토어 레인에 격리했다. Meta SDK 링크 실패는 EAS 빌드 소모 0회로 로컬에서 먼저 잡았고, 버전 게이트는 머지 전후 런타임 지문이 같아(iOS `af939b5b…`, Android `4452ee66…`) 기존 설치본이 OTA로 받을 수 있다.

## 방 꾸미기 편집기와 집 (2026.07 ~ 2026.11)

**과정**

- 방 꾸미기를 정해진 칸에 가구를 넣는 슬롯 방식에서, 가구를 아무 데나 놓고 회전·반전·크기·앞뒤 순서까지 바꾸는 캔버스 편집기(서버 형식 `FREE_V1`)로 전환했다.
- 같은 방은 나의 방, 친구 방, 집의 작은 미리보기 타일, 웹, 관리자 도구에 크기가 다르게 그려지고, 한 사용자가 폰과 웹에서 동시에 열 수도 있다. 그래서 저장되는 문서를 어떻게 정의할지가 화면 구현보다 큰 문제였다.
- 편집기 위에서는 선택 툴바, 겹친 가구의 터치 판정, 카탈로그 렌더 성능, 실행 취소를 차례로 다듬었고, 집 화면에는 서로 다른 개인 방을 한 장면에 합성하는 규칙을 만들었다.

### 해상도와 무관한 좌표 문서와 리비전 저장 충돌 설계 (2026.07)

**문제**

- 좌표를 무엇으로 저장할지, 두 기기가 동시에 편집하면 어떻게 할지, "저장 안 한 변경"을 어떻게 판정할지 세 가지를 정해야 했다.
- 화면 픽셀로 저장하면 큰 화면에서 놓은 가구가 작은 미리보기 타일에서는 방 밖으로 나간다. 배치는 전체 교체로 저장되어 나중에 저장한 기기가 먼저 저장한 편집을 조용히 덮어쓸 수 있었다.

**원인**

- 서버 계약은 위치를 방 렌더 영역 기준 0.0~1.0 정규화 좌표로 정했고, 서버는 `layoutRevision`과 요청의 `baseRevision`이 다르면 409 `ROOM_LAYOUT_REVISION_CONFLICT`를 돌려준다(낙관적 동시성 제어). 머지 전에 일회용 계정으로 실서버에서 이 동작을 직접 확인했다.
- 남은 질문은 비율과 기준 폭 같은 기하 상수를 화면마다 어긋나지 않게 두는 방법과, 409를 받았을 때 클라이언트가 할 일이었다.

**해결**

- 앱 모델을 서버 필드와 1:1로 맞추고, 렌더러는 좌표를 픽셀이 아닌 퍼센트 문자열로 배치해 모든 화면이 같은 코드로 그리게 했다. 비율·기준 폭·배율 범위는 렌더 계약 JSON 한 곳(`room-render-contract.v2.json`)에 모았다.
- 저장 결과는 `'ok' | 'conflict' | 'fail'` 세 갈래로 모델링하고, 충돌이면 "다른 기기에서 먼저 저장했어요" 모달에서 서버 상태를 다시 불러온다. 전체 교체라 두 편집본을 섞을 기준이 없어 자동 병합은 하지 않았다.
- 더티 체크는 저장 시점 스냅샷과의 문자열 비교로 했다. 성능 정리에서 비싼 직렬화만 `useMemo`로 감싸고 ref 기준값과의 비교는 매 렌더 하도록 나눴다. `dirty` 전체를 memo하면 저장 직후 낡은 `true`가 남아 저장 확인이 잘못 뜨기 때문이다.

**추가적인 문제**

- 서버는 좌표를 소수 5자리, 배율을 소수 2자리로 반올림해 저장하지만 저장 성공 시 캐시에는 응답이 아닌 보낸 본문을 쓴다. 다음 조회 전까지 반올림 오차만큼 달라질 수 있으나 측정하지는 않았다.

### 선택 툴바가 가구를 가리던 문제를 리렌더 없이 해결 (2026.07)

**문제**

- 선택 툴바(회전·반전·앞뒤 순서·빼기 6버튼)가 캔버스 상단 중앙에 고정되어, 벽 쪽에 둔 가구를 덮었다. 드래그 중에도 가구가 툴바 밑으로 들어가 놓는 위치가 보이지 않았다.

**원인**

- 고정 위치가 원인임은 분명했고 어려운 쪽은 해법이었다. 반투명 툴바와 캔버스 밖 고정은 각각 가림과 카탈로그 공간 잠식 때문에 버리고, 선택 가구가 상반부면 툴바를 아래로 보내는 위치 회피와 드래그 중 숨김을 합치기로 했다.
- 막힌 지점은 "드래그 중 숨김"이었다. `setDragging(true)` 같은 상태 변경은 리렌더를 일으키고, 리렌더는 진행 중인 팬 제스처를 취소한다는 규칙을 앞선 웹 스모크에서 이미 확인한 상태였다.

**해결**

- "드래그 중" 신호를 React 상태 대신 UI 스레드 `SharedValue` 하나(`dragActive`)로 전달했다. 팬 워클릿이 시작에 `true`, `onFinalize`에서 `false`로 쓴다. 취소·중단 경로에서도 실행되도록 `onEnd`가 아닌 `onFinalize`에 둔 것이다.
- 툴바는 `Animated.View`로 바꿔 숨길 때 `pointerEvents`도 `'none'`으로 바꿨다. 보이지 않는 빼기 버튼을 두 번째 손가락이 누르는 유령 터치를 막기 위해서다.
- 위치 회피는 선택 가구의 정규화 y가 0.5 미만이면 아래로 보내되, 선택과 드롭 시점에만 정했다. 드래그 중 실시간으로 바꾸면 경계에서 툴바가 튀기 때문이다.

**추가적인 문제**

- 드래그 중 fade는 웹 계측 한계로 자동 검증하지 못해 실기기 육안 확인 항목으로 남겼다. 프레임레이트도 측정하지 않았고 "드래그 중 리렌더 0회"는 구조상 보장되는 성질이다.

### 엉뚱한 가구가 잡히던 문제와 선택 게이팅·히트박스 축소 (2026.08)

**문제**

- 가구가 몰린 곳에서 눈으로는 아래 러그를 잡았는데 위의 램프가 끌려가거나, 선택한 가구를 옮기려 해도 이웃 가구가 움직였다.

**원인**

- 원인은 두 겹이었다. 선택 상태가 선택 링을 그리는 데만 쓰이고 팬(드래그) 제스처는 모든 가구에 조건 없이 붙어 있었다. 또 터치 영역이 가구 PNG의 투명 여백까지 포함한 정사각형 박스라서, z가 높은 가구의 보이지 않는 모서리가 아래 가구를 가렸다.
- 한쪽만 고치면 탭 선택 단계에서 투명 모서리가 선택을 가로채거나, 선택한 가구를 옮기다 이웃을 건드리는 문제가 남았다.

**해결**

- 팬에 `.enabled(selected)`를 걸어 선택된 가구만 조작을 받게 했다. 핀치도 같이 막아 편집 흐름을 "탭으로 고르고 고른 것만 조작"으로 바꿨다.
- 음수 `hitSlop`으로 박스 안쪽 78%(`HITBOX_RATIO`)만 터치를 받게 하되, 작은 소품을 못 집지 않도록 44pt 하한(`MIN_HIT_SIZE`)을 순수 함수 `hitSlopInset`으로 고정했다. 팬·탭·핀치에 같은 인셋을 적용해 선택과 조작이 같은 영역을 보게 했다.
- 후속으로 웹에서 가구를 아예 못 고르는 문제가 드러났다. 웹 RNGH(제스처 라이브러리)는 비활성 핸들러를 끝나지 않은 것으로 보고 탭을 계속 기다렸다. 선택 전에는 탭 하나만 조합하도록 바꿔 해결했다.

**추가적인 문제**

- 78%는 눈대중으로 정한 상수이고 가구 19종의 실제 아트 여백을 재서 정한 값이 아니다. 알파 마스크 기반 픽셀 히트 테스트가 정석이지만 이번 범위에서는 뺐다. 다른 가구를 옮기려면 항상 탭 후 드래그 두 단계가 된다.

### 방을 건드릴 때마다 카탈로그 전체가 다시 그려지던 문제 (2026.08)

**문제**

- 캔버스에서 가구 선택, 드래그 커밋, 크기 변경, 툴바 조작 중 무엇을 해도 아래 카탈로그 타일이 전부 다시 렌더됐다. 데모 카탈로그 10종, 방 가구 2개 조건에서 가구 한 번 선택에 타일 렌더가 12회 추가로 일어났다.

**원인**

- 그리드와 타일 5종에 memo가 없었다. 그렇다고 memo만 붙이면, 내려가는 콜백 12곳이 인라인 람다라 렌더마다 새 함수가 만들어져 얕은 비교가 실패한다. 경계와 참조 고정을 한 묶음으로 봐야 했다.
- 타일마다 `placed.includes`로 배열을 훑는 O(n) 비교가 있었고, 리뷰에서 `floors`/`backgrounds`의 기본값 `= []`이 렌더마다 새 배열을 만들어 memo를 연쇄 무효화하는 넷째 함정도 나왔다.

**해결**

- 그리드와 타일 5종에 `React.memo`를 세우고, 인라인 람다 12곳은 참조가 고정되는 `useStableCallback`으로 바꿨다. `placed` 조회는 `Set`으로 바꾸고, 기본값 `[]`은 모듈 상수 `NO_SURFACES`로 올렸다.
- 회귀 테스트는 렌더 횟수를 직접 단언하게 했다. 처음 쓴 느슨한 단언(`afterSelect < afterMount`)은 최적화 없이도 통과해 폐기했고, 최적화를 되돌리면 `Expected: <= 2 / Received: 12`로 실패하는 것을 확인했다.
- 같은 진단을 집 화면의 방 렌더(좌석 8~12칸)에도 적용했다. `assetSource()`가 키마다 같은 객체를 돌려주게 하고, 파생값 `useMemo`와 컴포넌트 memo를 더했다. 이후 1,837줄이던 화면을 나누고 웹 2단 레이아웃의 중복을 접을 때도 이 테스트가 경계 보존의 안전망이 되었다.

### 같은 방이 화면마다 다르게 보이던 문제와 렌더 계약의 자리 박스 구조 (2026.09)

**문제**

- 집 좌석의 작은 방에서는 캐릭터가 러그 위로 떠 보였고, 꾸미기 화면의 캐릭터는 나의 방보다 작았다. 꾸미기를 적용하고 집 탭으로 가면 내 좌석 썸네일이 예전 방으로 남아 있는 불일치도 있었다.

**원인**

- 네 화면 모두 계약의 같은 수치(폭 42%, 바닥 16%, 정사각)를 읽고 있어서 값이 아니라 적용 구조를 의심했다. 정상인 나의 방만 자리 박스(`Pressable`) 안에 아바타를 `100% × 100%`로 채우는 두 겹 구조였고, 나머지는 자리 스타일을 `CharacterAvatar`에 직접 넘겼다.
- `CharacterAvatar`의 기본 `size` 96이 만든 명시 `height: 96`이 `aspectRatio: 1`보다 우선해 박스가 "폭 42% × 높이 96px"이 되었다. 작은 방에서는 박스가 세로로 길어져 떠 보이고, 큰 방에서는 눌려 작아졌다. 썸네일은 미리보기 훅이 집당 한 번만 불러온 캐시를 저장 후 무효화하지 않은 별개 원인이었다.

**해결**

- 비인터랙티브 `Room`과 꾸미기 화면을 나의 방과 같은 두 겹 구조로 바꿨다. 바깥 `View`에는 계약 좌표만, 안쪽 아바타에는 `{ width: '100%', height: '100%' }`만 준다. 계약 값은 바꾸지 않고 적용 방법을 한 가지로 통일했다.
- 훅에 `invalidate()`를 추가해 꾸미기 `onApply` 성공 시 호출했다. 새 응답이 오기 전까지 기존 썸네일을 남겨 빈 타일 깜빡임을 막았다.
- 한 화면만 모서리를 각지게 하려고 공통 계약의 `borderRadiusPx`를 바꿨다가 다른 화면까지 바뀌어 되돌렸다. 공통 계약에는 모든 뷰포트가 공유하는 값만 두고 예외는 화면 쪽에서 덮어쓰는 경계를 이때 정했다.

**추가적인 문제**

- 회귀 테스트는 `Room`에만 추가했고 꾸미기 화면 쪽 단언은 아직 없다. 실기기에서 수정 전후를 나란히 측정한 수치도 없다.

### 서로 다른 개인 방을 한 집에 자연스럽게 합성 (2026.11)

**문제**

- 개별 방 전체를 새 집 그림 안에 넣으면 벽과 바닥, 원근이 서로 달라 붙여 넣은 느낌이 났다. 방 대신 가구만 배치한 첫 구성에서는 크기가 다른 이미지가 겹쳤다.

**원인**

- 개인 방의 좌표와 배경을 그대로 쓰는 방식은 집 그림의 층 구조와 조화를 보장하지 못했다. 중심점 간 거리만 띄워도 가구 이미지의 실제 너비와 높이가 다르면 겹침을 막을 수 없었다.
- 그래서 개인 방의 배치 좌표를 재사용하지 않고 공동집 자체의 표현 규칙을 정의하기로 했다.

**해결**

- 가구 없는 개방형 집 그림을 만들고, 실제 배치한 가구 중 최대 2개와 캐릭터를 서로 겹치지 않는 별도 사각형 안에서 `contain`으로 그렸다. 누르면 기존 전체 방이 열린다.
- 4명을 넘는 집은 본채와 별채로 나누되 화면 번호와 서버 `membershipId`를 분리해 방문 대상이 바뀌지 않게 했다. 기존 4종의 커버 키와 CDN 객체는 유지해 구버전과 호환했다.
- 후속으로 집 단위 `displayMode`(리디자인 집 또는 기존 집 형태)를 방장만 바꾸게 했고, 전환이 개인 방 배치나 저장된 테마를 바꾸지 않게 했다. Storybook에서 실제 집 화면을 쓰자 웹 번들링이 실패해, 순수 선택 함수를 리소스 계층으로 옮기고 기존 훅은 재수출했다.

**추가적인 문제**

### 명령 패턴 대신 스냅샷 스택으로 만든 실행 취소·다시 실행 (2026.11)

**문제**

- 방 꾸미기에는 되돌리기가 없어 가구를 잘못 빼거나 엉뚱한 곳에 놓으면 처음부터 다시 배치해야 했다. 되돌리기를 무엇으로 표현할지, 한 단계를 무엇으로 볼지, 선택 상태·저장 경고·저장 충돌과 어떻게 맞물릴지 정해야 했다.

**원인**

- 편집 지점이 화면 안에 9군데 흩어져 있어, 동작마다 역연산을 두는 명령 패턴은 맨 앞/맨 뒤처럼 여러 가구의 z를 바꾸는 동작에서 이전 값을 모두 들고 있어야 하고 어긋날 자리도 늘었다.
- 모든 갱신이 이미 불변 방식이라 스냅샷을 쌓아도 바뀌지 않은 가구는 같은 참조를 공유한다. 한 단계의 단위도 정해져 있었다. 드래그는 놓는 순간 한 번만 상태를 커밋하므로 그 지점이 곧 한 단계다.

**해결**

- 순수 리듀서와 훅 `useDecorHistory`(past / present / future, 최대 50단계)를 만들고, 기존 setter 4개의 시그니처를 유지한 채 히스토리 커밋으로 바꿨다. 9개 편집 지점의 코드는 0줄 바꿨다. 내용이 같은 커밋은 쌓지 않는다.
- 선택 상태는 히스토리 밖에 두고 되돌려 가구가 사라지면 선택만 푼다. 기존 더티 체크는 그대로 연동되어, 처음 상태까지 되돌리면 저장 확인이 뜨지 않는다.
- 후속으로 웹 키보드 단축키를 얹으면서 방향키 연타가 수십 단계를 만드는 문제는 800ms 안의 같은 키 커밋을 한 단계로 덮어쓰는 묶음 키로 풀었다. 스마트 가이드·스냅은 계산을 팬 워클릿 안에서 돌려 드래그 중 상태 변경을 피했다.

**추가적인 문제**

- 실기기에서 메모리와 프레임은 재지 않았다. 50단계 × 가구 수십 개 규모라 문제없을 것이라는 추정이다. 스냅 드래그는 웹 갤러리에서 다른 시트가 화면을 덮어 실측하지 못했다.

→ [사례 기록](2026-11-05-room-editor-undo-redo.md)

**최종 성과**

방 꾸미기를 해상도와 무관한 정규화 좌표 문서와 리비전 기반 저장으로 정리해, 같은 방을 여러 화면이 같은 코드로 그리고 동시 편집 충돌도 예상된 결과로 다루게 되었다. 렌더 횟수는 가구 한 번 선택에 12회에서 2회로, 집 화면 좌석 12칸 렌더는 3.75~~3.82에서 2.04~~2.10 ms/commit(−45%)으로 줄었고(Jest 측정, 실기기 측정은 없음), 선택·히트박스·실행 취소는 단위 테스트와 화면 테스트로 고정했다. 집 화면은 6종의 집 그림과 1, 3, 4, 6, 10명 구성에서 방문 대상이 보존되는 것을 테스트로 확인했다.

### 응답 유실과 헤드리스 작업이 만든 강제 로그아웃 (2026.09)

**문제**

- iOS, Android, 웹 모두에서 같은 기기인데 하루에도 여러 번 로그인 화면으로 나간다는 보고가 있었다. refresh 만료(14일)로는 설명되지 않았다.

**원인**

- 서버 설정으로 만료 가설을 배제하고, `AuthService.refresh`가 재사용이나 동시 회전 패배 때 회원 단위로 전체 폐기하는 것을 확인했다.
- 앱 코드에서 정상 사용 중 재사용이 생기는 경로를 찾았다. 서버가 회전을 커밋한 뒤 응답이 오기 전에 앱이 백그라운드로 가거나 네트워크가 끊기면 옛 토큰이 남는다. Android 앱 아이콘 헤드리스 작업이 자체 메모리의 refresh로 따로 회전하는 경합도 있었다.
- 원인을 확정할 데이터가 없어 서버 정책을 바꾸기 전에 계측부터 싣기로 했다.

**해결**

- 갱신 거부로 세션이 지워질 때 `session_forced_logout`(이유, 상태, 서버 오류 코드, 포그라운드 여부)을 GA4와 Sentry에 남겼다.
- 갱신이 4xx로 거부돼도 보낸 것과 다른 쌍이 저장소에 있으면 다른 맥락이 먼저 회전한 것으로 보고 그 쌍을 채택해 로그아웃하지 않는다(`session_refresh_adopted`).
- 헤드리스 백그라운드 조회에 `refreshOnUnauthorized: false`를 추가해 토큰을 회전하지 않게 했다.

**추가적인 문제**

- 강제 로그아웃의 실제 빈도와 경로는 배포 후 수집할 예정이었고, 서버의 유예 시간과 기기 단위 폐기 도입은 그 데이터를 본 뒤 결정하기로 했다.

### 앱이 떠 있을 때 초대 링크를 누르면 방 화면만 뜨던 딥링크 (2026.10)

**문제**

- 초대 링크를 누르면 집 신청 화면이 아니라 방 화면으로 가고 신청도 되지 않았다. 앱이 꺼진 상태(콜드 스타트)에서는 정상이었다.

**원인**

- 랜딩 주소와 웹 재현은 정상이었고, 에뮬레이터에서 `adb shell am start -d rougether://join?code=…`로 앱이 방 화면에 떠 있는 웜 스타트를 재현했다.
- 셸 마운트와 화면 전환에 임시 로그를 심어 보니 기존 셸이 코드를 받아 집 탐색으로 간 직후 셸이 하나 더 마운트됐다.
- `/join`이 `<Redirect href="/">`로 루트를 새로 열어 셸이 둘이 됐고, 가려진 옛 셸이 코드를 소비한 채 코드 없는 새 셸의 방 화면만 보였다.

**해결**

- 딥링크 라우트 공용 훅 `useDeepLinkHandoff`를 만들어 코드를 맡긴 뒤 뒤 화면이 있으면 `router.back()`으로 기존 셸로 돌아가고, 없을 때만 `replace('/')`를 쓰게 했다. 친구 초대(`/invite`)에도 같이 적용했다.
- 웜이면 `handoff` 뒤 `back`, 콜드면 `handoff` 뒤 `replace('/')`를 확인하는 회귀 테스트를 추가했다.

### 구글이 버튼을 iframe으로 바꿔 막힌 웹 구글 로그인 (2026.10)

**문제**

- PC 크롬에서 구글 로그인 버튼을 누르면 구글 창 없이 즉시 "구글 로그인에 실패했어요"가 떴다. 같은 날 앱 OTA와 서버 배포가 있어 그쪽을 먼저 의심하기 쉬웠다.

**원인**

- 가짜 토큰으로 운영 `/auth/google`이 정상 401을 돌려주는 것과 CORS preflight 200을 확인해 서버를 배제했다. 당일 배포도 로그인 경로와 무관했다.
- 운영 페이지에서 구글과 서버로 가는 요청이 하나도 없고 Sentry 보고만 나가는 것을 보고, 구글 창을 열기 전 앱 코드 안에서 실패한다고 좁혔다.
- 숨겨 둔 영역에 `div[role=button]`이 없고 구글 도메인 iframe만 있었다. 우리 코드는 교차 출처 iframe 안의 버튼을 찾지도 누르지도 못했고, 테스트 스텁은 예전 GIS를 흉내 내 이 변화를 잡지 못했다.

**해결**

- 공식 버튼을 직접 노출해 동작을 확인했지만 크기와 모서리가 카카오 버튼과 맞지 않아, 카카오 웹처럼 페이지 리다이렉트(`id_token` 응답) 방식으로 바꿨다.
- `state`와 `nonce`를 대조하고 토큰이 주소창에 남지 않게 프래그먼트를 즉시 지웠으며, 서버 변경은 없었다. Google Cloud Console에 승인된 리디렉션 URI를 등록했다.

### iOS에서 푸시 data가 비어 항상 알림함으로 가던 문제 (2026.10)

**문제**

- 채팅 푸시를 눌러도 채팅방으로 가지 않는다는 제보가 있었다. 확인해 보니 iOS에서는 어떤 푸시를 눌러도 알림함으로 갔고 Android는 정상이었다.

**원인**

- 앱의 탭 처리 경로에는 문제가 없어 입력값인 `content.data`를 의심했다. 서버는 FCM `data`를 APNs `userInfo` 최상위에 싣는다.
- expo-notifications 55.0.27 iOS 소스(`NotificationRecords.swift`)는 원격 푸시 data를 `userInfo["body"]`에서만 읽는데, 이는 Expo 푸시 서비스 형식이라 FCM 직접 발송에는 `body`가 없다는 것을 확인했다.
- `xcrun simctl push`로 서버와 같은 모양의 페이로드를 넣어 `content.data = null`이고 `trigger.payload`에 키가 있는 것을 재현했다.

**해결**

- `content.data`가 비면 iOS 푸시 트리거의 `payload`를 읽는 `pushDataOf(request)`를 만들어 탭, 포그라운드 수신, 표시 필터 세 곳에 적용했다. 채팅방을 보는 중 그 방 푸시를 거르는 필터도 iOS에서 동작하지 않던 것이 함께 고쳐졌다.
- 서버 페이로드와 네이티브 설정은 바꾸지 않아 JS만으로 OTA 배포가 가능했다.

→ [사례 기록](2026-10-28-ios-fcm-push-data-empty.md)

### 닫힘 애니메이션 종료와 iOS 모달 해제, 계정 전환 경계의 분리 (2026.11)

**문제**

- 공용 BottomSheet의 200ms 퇴장 애니메이션이 끝나면 닫힌 것으로 취급했지만, iOS native Modal의 해제 완료는 그보다 늦을 수 있어 이전 화면이 남은 채 다음 이벤트 화면이 열릴 수 있었다.
- 출석 응답이 늦게 오거나 응답 유실 뒤 재조회할 때 요청을 시작한 계정과 현재 계정이 다를 수 있었다. 리뷰에서 찾은 위험이며 실제 데이터 오염 사고를 확인한 것은 아니다.

**원인**

- JS의 표시 상태, 퇴장 애니메이션 종료, native 화면 해제를 하나의 상태로 취급했고, 공용 시트에 `onDismiss`가 없어 다른 화면이 해제 완료를 기다릴 방법도 없었다.
- `mounted`와 `rendered`를 분리하자 신고, 제작 가구 판매, 달력 입력 왕복 테스트 다섯 개가 실패했다. 테스트가 native `onDismiss`를 보내지 않고 시간 경과만으로 다음 화면이 열린다고 가정했기 때문이다.

**해결**

- iOS는 Modal을 `visible=false`로 유지하다가 native `onDismiss`가 온 뒤에만 존재 상태와 시트 대기열을 해제하고, Android와 웹은 다음 프레임에 해제한다. 이벤트는 단일 활성 화면으로 관리해 기존 시트가 닫히는 중이면 기다린다.
- 요청 전후 세션 사용자를 비교해 계정이 바뀌면 이전 출석의 후속 GET, 지갑 갱신, 캐시 갱신, 보상 연출을 중단한다. 출석 POST는 자동 재시도하지 않고 응답 유실은 서버 상태 재조회로 맞춘다.

**추가적인 문제**

- 위 검증은 소스와 테스트 범위이고, iOS 실제 기기의 native 전환 검증이나 운영 이벤트 공개를 뜻하지 않는다.

→ [사례 기록](2026-11-09-event-modal-dismissal-session-boundary.md)

**최종 성과**

딥링크 웜 스타트는 같은 에뮬레이터에서 추가 셸 마운트가 수정 전 1회에서 0회가 됐고, iOS 푸시는 시뮬레이터에서 배너 아이콘이 종(type 모름)에서 하트(`FRIEND_CHEER`)로 바뀌어 type을 읽게 됐다. 웹 구글 로그인은 운영에서 로그인 완료를 확인했고 전체 399 스위트가 통과했다. 강제 로그아웃은 원인 경로를 줄이는 수정과 계측을 먼저 실었으며 빈도 데이터는 배포 후 수집 예정이었다.

## 채팅과 가구 거래소 (2026.10 ~ 2026.11)

**과정**

- 루게더에서는 회원이 만든 가구를 지정가 주문으로 거래하는 거래소를 운영했다. 주문 접수와 엔진의 체결 처리가 분리돼 있고, 판매하는 보유분은 에스크로(거래 중 맡겨 두는 보관)에 묶였다.
- 사용자가 AI로 만든 가구는 방에 보관하다가 다른 사용자에게 판매할 수 있었다.
- 집 채팅에는 고양이 이모티콘 8종을 추가했다. 선택 패널, 반투명 미리보기, 받은 메시지에 같은 투명 WebP 에셋을 쓰고, 이모티콘과 글을 한 메시지로 보낸다.

### 구매 대기 중인데 구매 버튼이 계속 열려 있던 거래소 (2026.10)

**문제**

- 판매 주문이 없어 구매 주문이 대기 중인데도 상세 화면의 구매 버튼이 계속 활성화됐다. 사용자가 주문을 반복해 시도했고 서버는 중복 구매를 거절했다.

**원인**

- 상세 화면은 인벤토리의 실제 보유 여부만 확인했다. 주문 접수는 미체결 구매 주문과 엔진 처리 전 접수까지 검사하므로 조회 응답과 접수 검증의 조건이 달랐다.
- 판매자 승인 절차는 없었고, 판매 주문이 없을 때 구매 대기를 유지하는 엔진 동작은 정상이었다.

**해결**

- 보유 의미는 유지한 채 서버 상세 응답에 본인의 구매와 판매 대기 여부를 추가했다. 화면은 대기 중 재구매를 막고 내 주문 확인 경로와 자동 체결 조건 안내를 제공한다.
- 주문 처리 후에는 거래소 재조회를 기다린 뒤 시트를 닫고, 다른 기기의 주문 등으로 중복 구매가 거절돼도 상세를 갱신한다.

**추가적인 문제**

- 서버 상태 전이는 실제 DB 테스트로, 앱은 컴포넌트 테스트로 확인했고 운영 배포와 실기기 검증 결과는 기록에 포함하지 않았다.

### 사라진 것처럼 보이던 제작 가구와 고정가 판매 전환 (2026.11)

**문제**

- 사용자가 AI로 만든 가구가 사라졌다고 느꼈다. 제작자가 원본을 판매 등록해도 계속 보관할 것으로 기대했지만 보유분 판매는 가구함에서 숨기고 방 배치도 제거했다.

**원인**

- 생성 실패와 서버 재시작을 먼저 확인했으나, 운영 생성 이력에는 생성 성공과 보관함 지급이 있었고 이후 같은 가구의 보유분 판매 주문이 있었다. 삭제처럼 보인 현상은 판매 에스크로 처리와 연결돼 있었다.
- 해당 주문을 정상 취소 경로로 처리해 원본을 반환했다. 취소는 가구함은 복구하지만 이전 방 배치까지 복원하지는 않는다.

**해결**

- 제작자는 원본을 유지하고 가격만 정해 수량 제한 없이 판매하고, 구매자는 같은 가구를 한 번만 사며 재판매는 제공하지 않는다. 구매 확인 시점의 가격과 `requestId`를 보내고, 응답 유실 재시도는 같은 키를 쓰며, 가격이 달라지면 서버가 거절한다.
- 서버는 구매자 차감, 제작자 지급, 가구 지급, 영수증, 원장을 한 트랜잭션으로 처리한다. 구 주문이나 미반환 에스크로가 남아 있으면 새 구매를 막고 기존 엔진의 취소 경로로 정리한다.
- 설치본 네이티브 입력이 dev와 달라, 기존 production 소스에 JS 변경만 적용한 OTA 후보를 따로 준비하고 플랫폼별 런타임이 일치할 때만 게시했다.

**추가적인 문제**

- 기존 production 런타임의 iOS 시뮬레이터에서 숫자 키보드가 가격 입력칸과 판매 버튼을 가렸다. 판매 시트가 가격 입력으로 바뀌었는데 공통 BottomSheet의 `avoidKeyboard`를 켜지 않은 것이 원인이어서 이를 활성화했고, 실제 배포 앱에서 후속 검증하기로 했다.

### 이모티콘 WebP가 iOS 설치본에서 보이는지 따로 확인하기 (2026.11)

**문제**

- 브라우저에서는 이모티콘이 표시됐지만 그 결과만으로 iOS 설치본의 이미지 디코더가 같은 WebP를 지원하는지는 알 수 없었다.

**원인**

- 초기 구현의 세 컴포넌트는 React Native 기본 `Image`를 썼다. 설치된 React Native 소스의 `Libraries/Image/ImageProps.js`는 WebP 지원을 Android 한정으로 설명한다.
- Expo SDK 55 Image 문서는 WebP를 iOS, Android, 웹에서 지원한다고 명시하고, 기존 채팅 사진 컴포넌트도 이미 `expo-image`를 쓰고 있었다.

**해결**

- 선택 패널, 선택 미리보기, 받은 메시지의 이모티콘을 `expo-image`의 `Image`로 통일하고 `contentFit="contain"`을 적용했다. 새 네이티브 의존성이나 앱 설정 변경은 없어 재빌드 없이 OTA로 갈 수 있다.

**추가적인 문제**

- 확인 범위는 코드, 공식 문서, 자동 테스트이며 실기기에서 그림이 표시된다는 확인은 별도 항목으로 남았다.

### 이모티콘 더블 탭 전송과 남은 사진 초안의 오발송 방어 (2026.11)

**문제**

- 같은 이모티콘을 빠르게 두 번 누르면 보내기 버튼 없이 전송하는 동작을 추가했다. 기존 중복 방어는 전송 후 패널이 열려 있는 상태에 의존했는데, 패널을 닫으면 남은 사진 초안 때문에 보내기 버튼이 다시 활성화될 수 있었다.
- 첫 선택과 두 번째 탭 사이에 React 렌더가 끝났다고 가정할 수도 없었다.

**원인**

- 첫 선택과 다음 탭을 한 `act` 안에서 호출하는 테스트로 렌더 전 연속 입력을 재현했다. 선택한 key와 마지막 탭 시각을 ref로 즉시 갱신해야 두 번째 콜백에서 쓸 수 있었다.
- 리뷰에서 키보드가 유지된 입력란은 `onFocus`가 다시 발생하지 않는 경계가 지적돼, 사진 재개 테스트를 강제 focus 대신 `pressIn`으로 바꾸고 이미 포커스된 입력란의 명시적 탭도 처리했다.

**해결**

- 동일 key, 현재 선택, 300ms 이내 연속 탭을 확인하고, 더블 탭과 보내기 버튼이 같은 전송 함수를 쓰게 했다. 전송, 취소, 패널 전환에서 탭 기록을 초기화한다.
- 전송 후 사진은 보존하되 새 사용자 조작 전까지 사진 보내기를 보류해 같은 렌더와 다음 렌더의 연속 전송을 막았다. 글이 있으면 패널을 닫고 없으면 유지하며 키보드는 강제로 닫거나 열지 않는다.

**추가적인 문제**

- 실제 기기의 키보드와 연속 터치는 별도 확인 범위로 남았다.

→ [사례 기록](2026-11-15-chat-emoticon-double-tap.md)

**최종 성과**

거래소는 구매 대기와 실제 보유를 구분해 반복 구매 시도를 막았고, 고정가 전환 뒤 운영 DB에서 V95 적용 성공, 남은 OPEN 주문 0건, PENDING 명령 0건, 미반환 오류 0건을 확인했다. 채팅 이모티콘은 이미지 렌더러를 `expo-image`로 통일하고 더블 탭 전송을 방어했으며, 관련 3개 테스트 모음 47개와 전체 475개 모음 4,049개 테스트가 통과했다. 실기기 표시와 키보드 동작은 별도 확인 항목으로 남았다.

### 튜토리얼 코치마크가 엉뚱한 곳을 짚고, 재시작하면 튜토리얼이 사라졌다 (2026.09)

**문제**

- 온보딩 직후 미션을 안내하는 코치마크(대상 버튼만 뚫어 강조하는 오버레이)가 데스크톱 웹에서 선물 버튼이 아니라 오른쪽 빈 곳을 강조했다. 이어서 iOS와 Android에서도 위치가 어긋난다는 보고가 있었다.
- 튜토리얼 도중 앱을 껐다 켜면 튜토리얼이 사라지고 다시 나오지 않았다.

**원인**

- Playwright로 1600px 창에서 재 보니 버튼은 창 기준 x=616, 앱 프레임은 x=200에서 시작했다. 대상은 창 기준 좌표로 등록되고 오버레이는 프레임 안에 그려져 원점 차이만큼 밀렸다.
- 네이티브는 좌표를 `onLayout`에서 한 번만 쟀는데, `onLayout`은 스크롤이나 탭 이동처럼 창 기준 위치만 바뀔 때는 불리지 않아 좌표가 낡았다. 진행 단계와 시작 조건은 메모리 상태뿐이라 재시작하면 초기화됐다.

**해결**

- 오버레이가 자기 루트의 창 원점을 `measureInWindow`로 재서 대상 좌표에서 빼도록 좌표계를 통일했다(`toOverlayRect`).
- 오버레이가 떠 있는 동안 250ms마다 원점과 대상을 다시 재고, 말풍선은 넓은 프레임에서 최대 420px로 줄였다.
- 진행 단계를 `progress:<단계>` 키로 저장해 재시작하면 그 단계부터 이어 간다.

**추가적인 문제**

- 같은 날 데스크톱에서 "안 고쳐졌다"는 재보고가 왔다. 구멍 자리의 터치까지 `pointerEvents="auto"`인 오버레이 루트가 가로채 버튼이 눌리지 않았고(`elementFromPoint`로 확인), 대상 래퍼가 버튼 안쪽만 감싸 테두리도 작았다. 루트를 `box-none`으로 바꾸고 버튼 전체 기준으로 측정하게 고쳤다. 첫 수정은 맞았지만 다른 원인이 하나 더 있었다.

### 웹 바텀시트 양옆에 검은 선이 생겼다 (2026.09)

**문제**

- 웹에서 루틴과 투두 작성 시트를 열면 시트 양옆에 검은 세로선 두 줄이 보였고, 넓은 창에서도 시트가 폰 폭에 갇혀 있었다. 작성 시트뿐 아니라 모든 바텀시트가 같았다.

**원인**

- 브라우저에서 `getComputedStyle`로 재 보니 시트 래퍼는 폭 480에 `border-left`가 1px 검정(`rgb(0,0,0)`)이었다.
- 시트는 공용 `BottomSheet`와 `ModalFrame`을 지나는데, `ModalFrame`이 앱 프레임용 스타일(`innerFramed`)을 재사용했다. 앱 프레임은 테두리 색을 토큰으로 따로 넘기지만, RN `Modal`은 프레임 밖 body에 포털로 붙어 색 없이 폭만 적용돼 기본 검정이 됐다. 수정 전 코드와 대조 실측으로 확정했다.

**해결**

- `ModalFrame` 전용 스타일로 분리했다. 폰 컬럼 창(480~959px)은 폭 480에 테두리 없음, 2단 창(960px 이상)은 새 토큰 `SHEET_FRAME_MAX_WIDTH`(640)까지 넓혔다.
- 하이드레이션과 겹쳐 동적 width가 DOM에 안 실리던 과거 함정을 피하려고 폭은 정적 StyleSheet 항목으로 뒀다. 공용 경로 한 곳 수정으로 모든 시트에 반영됐다.

### 웹에서 체크 상태와 진행 값이 사라지는 접근성 버그 (2026.09)

**문제**

- 스토리북 접근성 검사(axe)를 경고로 켜 보니 색 대비를 빼고도 ARIA 위반이 50건 이상이었다.
- 체크와 토글은 `role`이 있는데 `aria-checked`가 없고, 진행 바에는 이름과 값이 없었으며, 확인 다이얼로그에는 `role`이 빠져 있었다.

**원인**

- 컴포넌트에는 `accessibilityState`와 `accessibilityValue`가 이미 있어 네이티브에서는 정상이었다. `react-native-web` 0.21.2의 `createDOMProps`를 읽어 보니 이 객체 props는 매핑 대상이 아니라 웹 DOM에서 조용히 사라졌다.
- 다이얼로그는 RN Web `Modal`이 `role="dialog"`를 `onShow` 이후에만 붙여 애니메이션 중 검사가 과도 상태를 잡았다. 휠 피커 중첩은 웹이 줄 버튼을 따로 포커스 가능하게 내보내서 생겼다.

**해결**

- 객체 props를 네이티브와 웹이 모두 해석하는 개별 `aria-*` props(`aria-checked`, `aria-valuenow` 등)로 바꿨다. 네이티브는 이를 기존 상태 값으로 합쳐 VoiceOver와 TalkBack 동작이 유지된다.
- 진행 바, 로딩, 시트에 이름을 주고, 다이얼로그 스토리는 `role="dialog"`가 붙은 뒤 검사한다. 스토리북 접근성 검사는 color-contrast만 제외하고 `error`로 올려 이후 ARIA 회귀를 CI가 막게 했다.

**추가적인 문제**

- 휠 피커의 nested-interactive 1건은 웹 한정 구조 차이라 사유를 적은 스토리 단위 예외로 남겼다.

→ [사례 기록](2026-09-17-rn-web-aria-state-mapping.md)

### 안드로이드에서만 뽑기 버튼 아래가 잘렸다 (2026.10)

**문제**

- 갤럭시 S25 사용자가 뽑기 화면의 `1회 뽑기`, `5+1회 뽑기` 버튼 아래쪽(가격 줄)이 화면 밖으로 잘린다고 제보했다. 같은 폭의 웹과 iOS는 정상이었다.

**원인**

- 하단 인셋 누락 가설과 컨테이너가 화면보다 크다는 가설은 코드와 사용자 답변으로 배제했다. 스토어 빌드로는 로그인할 수 없어 로컬 Gradle 개발 빌드와 S25 해상도로 맞춘 에뮬레이터에서 같은 증상을 재현했다.
- 층마다 `onLayout`을 찍어 보니 화면 루트는 832로 정상이었고 버튼 줄은 18.1, 버튼은 72.2였다. 버튼이 줄 밖으로 54dp 넘친 것이다. 스크롤에 `flex: 1`을 주는 첫 수정은 효과가 없었고 이 수치가 이유를 알려 줬다.
- 버튼에 남은 `flex: 1`이 세로 방향에서 `flexBasis: 0`, 즉 높이 기준 0이 되어 Yoga(React Native의 레이아웃 엔진)가 줄을 18dp로 계산했다.

**해결**

- 버튼의 `flex: 1`을 제거했다. 폭은 래퍼가 나누고 버튼은 기본 `stretch`로 채운다. 같은 에뮬레이터에서 두 버튼이 가격까지 보이는 것을 캡처로 확인했다.
- jest는 레이아웃을 계산하지 않으므로 원인 스타일(버튼에 `flex` 없음, `minHeight` 있음)을 직접 잠그는 회귀 테스트를 넣었다.

### 달력 날짜를 누르면 원이 튀고 화면이 버벅였다 (2026.11)

**문제**

- 달력에서 날짜를 누르면 같은 자리의 달력이 그 주 한 줄로 접히는 주간 보기로 바뀌고, 선택 날짜의 원이 칸 사이를 미끄러진다. 이때 원이 튀거나 흔들리고 화면이 버벅였다.

**원인**

- 코드 추적으로 네 가지가 겹침을 확인했다. 방 화면을 하나 더 마운트해 JS 스레드가 바쁜 상태에서, 줄 접힘과 헤더가 둘 다 JS 드라이버로 도는 height 애니메이션이었고, 원은 늦게 오는 `onLayout`마다 순간이동하며 계단식으로 쫓아갔다.
- 웹에서 `requestAnimationFrame`으로 원과 목표 칸의 거리를 재니 스프링이 −192px에서 +25px로 지나쳤다 돌아오며 약 350ms에 정착했다.

**해결**

- 접히는 동안은 떠 있는 원을 숨기고 선택 칸 배경을 칠한다. 줄 접힘과 헤더는 Reanimated `useAnimatedStyle`과 `withTiming`으로 UI 스레드에 옮겼고, 스프링은 임계 감쇠(`bounciness: 0`)로 바꿨다.
- 이후 주간 보기를 새 화면이 아니라 페이저의 달력 페이지가 제자리에서 바뀌는 모드로 바꿨고, 원 좌표를 RN `Animated`에서 Reanimated 공유 값으로 옮겼다.
- 지나침은 +25px에서 0이 됐고, 복귀 녹화의 빈 프레임은 5개에서 0개가 됐다.

**추가적인 문제**

- 주간 보기에서 나올 때 달력이 깜빡였다. 개발 번들과 에뮬레이터 수치는 실행마다 흔들려 릴리스 APK의 같은 세션 A/B와 녹화 프레임으로 판정했고, 페이저 폭 초기값, 첫 등장 페이드, Android에서 네모로 그려진 칸 채움을 차례로 고쳤다.
- 실기기 녹화로 탭 직후 약 9프레임(300ms) 정지가 확인돼 위의 제자리 전환으로 이어졌다. 돌아가는 길의 원 사라짐과 16dp 튐은 방향별 접힘 상태와 gap 애니메이션으로 고쳤다.
- 두 차례 같은 제보가 이어졌다. 접힌 뒤 원이 두 줄 아래에 남는 문제는 마지막 `onLayout`이 오지 않아서였고, 테스트만 통과한 채 "실기기 확인 대기"로 닫은 수정이 맞지 않았다. 에뮬레이터에서 재현하니 중단된 네이티브 애니메이션이 끊긴 시점의 값을 늦게 되돌려 써서 원이 약 526px 아래에 섰고, "이미 선택된 날짜를 다시 누르면 정상"이라는 한 쌍으로 원인이 갈렸다.

### 멈춰 둔 캐릭터가 Android에서만 다시 움직였다 (2026.11)

**문제**

- 캐릭터의 움직이는 webp를 첫 장면에 멈추기로 하고 expo-image의 `autoplay={false}`를 줬다. 웹은 앱에 든 정지 그림으로 바꿔 해결했는데, Android 앱에서는 캐릭터가 여전히 움직인다는 제보가 왔다.

### 한글을 지우면 앞 글자도 사라진 이유는 비어 있는 폰트 윤곽이었다 (2026.11)

**문제**

- 아이폰 사용자가 닉네임 입력 중 글자가 사라진다고 제보했다. iOS 27에서 `루게더`를 입력하거나 마지막 음절을 지우며 `겓`을 거치면 입력창에 `루`만 보이고 뒤에는 빈 공간과 커서가 남았다.

**원인**

- 처음에는 iOS 한글 조합 상태와 controlled value 충돌을 의심했지만, 조합과 삭제를 합성한 UIKit 테스트는 수정 전 코드에서도 정상이었다.
- `cmap` 등록 여부만 보면 기본 폰트도 한글 전체를 지원하는 것처럼 보였다. `fontTools`의 `BoundsPen`으로 실제 윤곽까지 검사하니 NanumSquareRound는 11,172자 중 2,479자, SUIT는 2,668자만 윤곽이 있었다. `겓`은 등록돼 있고 폭도 있으나 윤곽이 없어 OS 폰트 대체 없이 빈 공간으로 그려졌다. 네이티브 재현에서도 입력값과 JS 상태는 `루겓`인데 화면에는 `루`만 보였다.

**해결**

- 입력창의 글꼴 선택을 공용 `AppTextInput`에 모았다. 윤곽이 불완전한 폰트는 앱에 이미 든 Pretendard의 같은 굵기로 대체하고, 일반 화면의 폰트 정책은 유지했다. 모든 네이티브 입력 사용처를 이 컴포넌트로 연결했고, 값 동기화를 바꾸던 가설 단계의 수정은 제거했다.
- 웹은 대체 패밀리도 중복 없이 등록하게 맞췄다. 폰트 파일 SHA-256과 윤곽 감사 결과를 잇는 회귀 검사를 넣었다.

**추가적인 문제**

- 검증은 코드와 로컬 네이티브 하니스 기준이며 사용자 아이폰에 배포한 결과와는 구분한다. 키 입력 자동화가 아니라 UIKit 조합 API를 쓴 재현이다.

- 시뮬레이터는 네이티브 재빌드 대신 `expo export:embed`로 만든 JS 묶음을 설치된 앱 안의 `main.jsbundle`과 바꿔 확인했다.

### React Native 컴포넌트를 브라우저 테스트 파이프라인에 올렸다 (2026.09)

**문제**

**원인**

- 스토리 `render`에서 Storybook의 `useArgs`와 React 훅을 섞었다. 로그의 `new dependencies optimized ... reloading`을 단서로, 테스트 중 Vite가 늦게 발견한 의존성을 다시 묶으며 React가 두 벌 로드된 것을 확인했다.

- 폰트 래스터가 OS마다 달라 시각 회귀 기준 이미지는 linux(CI)에서만 만들고 비교한다. `package.json` scripts와 `.gitignore`는 런타임 지문 입력이라 건드리지 않고, CI에서 CLI를 직접 호출하며 devDependencies만 추가했다.

**추가적인 문제**

- CI가 만든 기준 이미지를 열어 보니 다크 카드 스토리의 캔버스가 내용 높이(190px)까지만 칠해져 있었다. 그대로 커밋하면 버그를 기준으로 고정할 뻔했다. 측정으로 `#storybook-root`가 flex 컨테이너가 아니어서 `flex: 1` 래퍼가 늘어나지 않는 것이 원인임을 확인해 `display: flex`로 고쳤다.

### 1,400개 넘는 i18n 키를 충돌 없이 나눠 끝냈다 (2026.09)

**문제**

- 도메인별 병렬 진행 시 모두가 같은 `ko.json`과 `en.json`을 고쳐 머지 충돌이 매번 났다. 한 PR이 CI에서 `TS2448 Block-scoped variable 'tr' used before its declaration`으로 실패했고, 자동 리뷰는 로그인한 모든 사용자가 앱을 열자마자 크래시한다고 판정했다.
- 미니게임(WebView 안의 HTML 문자열)과 Android 홈 위젯(별도 헤드리스 태스크)은 앱의 i18n 인스턴스에 닿지 않았고, 서버 값과 매칭하는 한국어 데이터 키는 번역하면 안 됐다.

**원인**

- 충돌은 도메인 분할이 코드에는 있고 리소스 파일에는 없어서 생겼다. 크래시 위험은 `useCallback` 의존성 배열에 `tr`을 넣었는데 `const tr = useT()`가 훨씬 아래에 있어 렌더 시 TDZ(선언 전 접근) 에러가 난 것이었고, 멈춘 PR이 이틀 방치되며 dev와 충돌이 쌓였다.

**해결**

- 리소스를 `resources/{ko,en}/<domain>.json`으로 쪼개 코드와 리소스 소유를 1:1로 맞췄다. 병합 키 수와 파일별 키 수 합이 같은지, ko와 en의 누락, 빈 값, 보간 변수 불일치를 막는 테스트를 넣었다.
- 마무리 5갈래를 git worktree로 격리해 담당 파일을 겹치지 않게 병렬로 올렸고, 멈춘 PR은 닫고 최신 dev에서 재작업해 `useT()` 선언을 위로 올렸다.
- 미니게임은 HTML 생성 시점에 사전을 주입하고, 위젯은 앱이 요약과 함께 저장한 언어 코드로 조회한다. 서버 값과 매칭하는 문자열은 유지하고 표시만 번역했다.

**추가적인 문제**

- 서버가 완성문으로 내려주는 알림과 푸시 문구는 앱에서 풀 수 없어 서버 이슈로 분리했다. iOS 위젯은 Swift 변경이 네이티브 빌드를 요구해 요약에 `lang`만 미러하고 다음 네이티브 윈도우로 넘겼다.
- 영어 레이아웃 감사에서 알림 헤더가 390px에서도 잘려 영어 문구를 짧게 고쳤다. 320px의 나머지 잘림은 RN Web이 `adjustsFontSizeToFit`을 지원하지 않는 웹 한정 한계라 실기기 확인 전에는 고치지 않았다.

### 성능 추적을 켜면 웹 API가 통째로 막힐 뻔했다 (2026.09)

**문제**

- Sentry 성능 추적을 켜는 한 줄 설정이 웹앱(app.rougether.com)의 모든 API 호출을 깨뜨릴 수 있었다. 네이티브 테스트는 통과하고 운영 웹에서만 로그인과 조회가 일제히 실패하는 종류의 사고였다.

**원인**

- 설치된 `@sentry/react-native` 7.11 소스를 읽으니 요청 계측은 `tracePropagationTargets`에 맞는 URL에 `sentry-trace`와 `baggage` 헤더를 붙이고, 기본값이 네이티브는 모든 URL, 웹은 같은 출처만으로 플랫폼마다 달랐다.
- 웹앱과 API는 출처가 달라 커스텀 헤더가 붙으면 브라우저가 사전 요청(preflight)을 보낸다. 서버 CORS 허용 헤더는 `Authorization, Content-Type, Accept, Origin`뿐이라 거부될 것이었고, 서버에는 Sentry가 없어 헤더를 받아도 이어 볼 곳이 없었다.

**해결**

- `tracePropagationTargets: []`로 전 플랫폼 전파를 끄고 스팬만 남겼다. 스팬은 `shouldCreateSpanForRequest`로 우리 API 요청에만 만든다.
- 후속 순서(서버 CORS 허용 헤더 추가 후 전파 대상을 API로 좁혀 켜기)를 문서에 못 박았다.
- 초대코드가 쿼리에 실리는 요청이 있어 `beforeSendSpan`과 `beforeBreadcrumb`에서 쿼리와 해시를 지우고 숫자 id를 `{id}`로 바꿨다. 문서에 `expoRouterIntegration`이 있었지만 설치된 7.11에는 없어 SDK 소스를 확인하고 `reactNavigationIntegration` 방식으로 구현했다.

**최종 성과**

스토리는 47개에서 82개로, Vitest 브라우저 테스트는 29 파일 82 테스트 통과로 늘었고 시각 회귀 12장이 CI에서 재실행 비교로 일치했다. i18n 키는 ko와 en 각 1,569개(도메인 파일 9개)가 됐고 마무리 PR 5개를 동시에 진행하면서 리소스 파일 충돌은 0이었다. 트레이스 전파 헤더는 0개라 웹 API preflight에 영향이 없으며, 운영 샘플링 20%로 무료 한도 안에서 화면 전환과 API 구간을 추적한다.
