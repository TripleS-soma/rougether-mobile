# 탭 페이저 안에 집 페이저 넣기 — 같은 축의 스와이프를 다시 나누기

- 2026-10-25 / house(제스처·레이아웃) / 이슈 #1575, 선행 결정 #761·#563·#1347
- 키워드: React Native Gesture Handler, 중첩 페이저, 제스처 중재, Reanimated UI 스레드 애니메이션, 절대배치 레이아웃, 웹 실측

## 배경

앱의 하단 탭은 인스타그램식 가로 페이저(#563)다. 본문 어디서든 가로로 밀면 탭이 넘어간다. 집 탭 안에는 여러 집이 있고, 집을 넘기는 수단은 화면 양 끝의 `‹ ›` 화살표뿐이었다. 원래는 집도 가로 플링으로 넘겼는데 #761에서 **뺐다** — 같은 손동작이 손가락 위치에 따라 탭이 되기도 하고 집이 되기도 해서 예측할 수 없었기 때문이다.

사용자 요청은 그 결정을 뒤집는 것이었다. 집 탭에서는 가로 스와이프로 집을 넘기고, 탭 전환은 바텀바에서만 한다. #761의 문제는 "같은 축을 두 제스처가 다투는 것"이었으니, **축을 나누는 기준을 손가락 위치가 아니라 탭으로 바꾸면** 모호함 없이 되돌릴 수 있다. 집 탭 본문 = 항상 집, 탭 전환 = 항상 바텀바.

## 문제 (요구 사항과 제약)

- 손가락을 따라 옆 집이 끌려 들어와야 한다(사용자 선택). 집 화면은 983줄짜리 한 컴포넌트로, 카메라(핀치 줌·팬), 좌석 꾹 눌러 드래그, 방 미리보기 수십 장을 들고 있다. 이걸 두세 벌 띄울 수는 없다.
- 확대 중 한 손가락 이동은 카메라 팬이어야 하고(#1347), 좌석 드래그와 도트 꾹 눌러 순서 바꾸기도 살아 있어야 한다.
- 탭 페이저에는 이미 플랫폼별 수정이 쌓여 있다 — iOS 스크롤 중재(#1150), 취소된 팬의 래치 고착, 이웃 페이지 노출 범위(성능 장부 M1). 새로 짜면 이걸 다시 밟는다.
- 네이티브 지문을 바꾸면 안 된다. JS만 바꿔 OTA로 기존 설치본에 보내야 한다.

## 원인 분석 (가설 → 검증 과정)

### 설계

탭 페이저를 **재사용해 집 화면 안에 하나 더 넣었다.** 바꾼 건 옵션 두 개뿐이고 기본값은 탭 페이저 그대로다(기존 테스트 41건 무변경 통과).

- `bounceEdges` — 끝에서 바깥으로 끌면 저항(0.35배, 화면 폭 18% 상한)을 받으며 따라왔다가 돌아온다. 탭 페이저는 iOS에서 끝 방향 터치를 **놓아** 바깥 제스처가 받게 하는데, 집 탭은 바깥(탭 페이저)이 잠겨 있어 놓으면 아무도 안 받는다. 그래서 잡는다.
- `testID` 접두 — 같은 화면에 페이저가 둘이 되므로.

중재는 새로 짤 필요가 없었다. 카메라는 `manualActivation`으로 8px에서 먼저 활성화되고, RNGH 기본 배타성으로 아직 24px에 못 간 페이저를 취소한다. 맥락이 아니라 제스처 일반 규칙이라 안쪽 페이저에도 그대로 먹는다. 좌석 드래그 중임은 이미 `draggingSV` 공유값으로 있어서 그대로 집 페이저 잠금이 됐다 — React Compiler가 막는 공유값 쓰기(#748)를 새로 만들 필요도 없었다.

옆 집은 **가벼운 미리보기**다. 카메라·드래그·방문 탭은 실제 집 한 벌에만 두고, 미리보기는 하늘·스위처·프레임·좌석 타일만 그린다. 방은 이미 받아 둔 캐시가 있을 때만, 없으면 타일의 아바타 폴백. 현재 집의 양옆 한 칸만 그리고 더 먼 칸은 빈 하늘이다. 정착하면 그 자리가 실제 화면으로 바뀌는데, 정착 애니메이션은 Reanimated가 UI 스레드에서 돌리므로 JS가 실제 화면을 마운트하느라 바빠도 슬라이드는 끊기지 않는다.

정렬은 **같은 계산을 공유해서** 보장했다. 프레임 높이는 집 커버(1·2·3층)와 측정한 헤더·내비 높이로 정해진다. 미리보기와 실제 화면이 1px이라도 다르면 넘어가는 순간 집이 튄다. 그래서 크기 계산(`fitHouseFrame`)·레이아웃 스타일·배경·알약을 `house-scene`으로 빼고 둘이 같이 쓰게 했다.

### jest가 못 잡은 것 — 웹 실측으로 잡은 세 가지

단위 테스트(제스처 핸들러를 직접 호출)는 전부 통과했다. 그다음 웹에서 Playwright로 실제로 끌어 보니 세 가지가 나왔다.

**1) 레일 위에서 시작한 스와이프가 안 먹었다.** 화면 오른쪽에 떠 있는 레일(목표·집 탐색·집 관리)을 "같이 밀리지 않게" 페이저의 **형제**로 뺐다. 그런데 RNGH 제스처는 자기 `GestureDetector` 서브트리의 터치만 받는다. 첫 측정에서 왼쪽 끌기가 아무 반응이 없었고, 시작점 좌표가 정확히 "목표" 버튼(295, 318) 위였다. 예전엔 레일도 탭 페이저 안이라 레일 위에서 밀어도 탭이 넘어갔으니 퇴보다.
→ 페이저에 `overlay` 슬롯을 만들어, 레일을 **제스처 영역 안, 미끄러지는 줄 밖**에 그렸다. 탭은 버튼이, 24px 넘는 끌기는 페이저가 가져간다. 재측정에서 레일 위에서 시작해 다음 집으로 넘어갔다.

**2) 갤러리 항목 하나가 통째로 사라졌다.** 첫 측정의 `house-pager` 상자가 `width: 0, height: 0`이었고, 그 안의 "다음 집" 버튼은 클릭이 30초 타임아웃났다. 탭 페이저의 페이지는 `position: absolute`라 **부모 크기에 기여하지 않는다.** 셸에서는 집 화면이 탭 페이저의 한 칸(위아래 0 고정)에 들어가 높이가 늘 정해져 있지만, Dev 갤러리의 `HouseSixSeatViewport`는 높이 없는 카드에 집 화면을 그대로 넣었다. 예전엔 세로 스크롤이 내용만큼 펴져서 보였는데, 이제 0으로 접혔다.
→ 집 화면을 끼워 쓰는 곳은 셸과 갤러리뿐이라 실제 앱은 안전했다. 갤러리 항목은 `viewport=1` 단독 모드(#1163, 기기 화면 크기를 그대로 재야 함)와 목록 모드를 구분해 목록 모드에서만 높이를 줬다. 재측정 326×760.

**3) 겹친 페이저가 바깥의 '보이는 중'을 덮어썼다.** 페이저는 페이지마다 `PageActiveContext`로 "이 페이지가 보이는 중인가"를 내려 준다. 집 안의 온라인 점·스피커 애니메이션이 이걸 읽는다. 안쪽 페이저가 생기면서 집 페이지들은 **안쪽** 값만 보게 됐다 — 다른 탭에 있는데도 현재 집은 '보이는 중'이다. 이건 실측 전에 코드를 읽다 잡았다.
→ 페이지가 바깥 맥락과 AND한다. 수정 전 코드에서 실패하는 테스트로 잠갔다.

## 결과 (수치)

- **정렬**: 프레임 높이가 다른 두 집(610.08px / 475.59px) 사이에서, 끌기 중 미리보기 프레임 `y 480.40625 · h 475.59375`와 정착 후 실제 프레임 `y 480.40625 · h 475.59375`가 같다.
- **웹 실측**: 레일 위·프레임 위에서 시작한 스와이프 모두 집 전환, 첫 집에서 바깥으로 밀면 저항을 받으며 따라왔다가(프레임 x 0 → 35) 돌아옴, 레일 버튼 탭은 그대로 동작, 집 탭 스와이프로 탭이 넘어가지 않음, 바텀바로 탭 전환.
- **지문**: 1.5.4 스토어 빌드와 동일(iOS `af939b5b…` · Android `4452ee66…`) — OTA로 기존 설치본에 도달.
- **테스트**: 411 스위트 / 3,410건 통과. #761·#1347을 고정하던 테스트 3건은 새 의도로 바꿨다(탭 페이저 잠금, 확대 중 집 페이저는 안 잠김, 좌석 드래그 중엔 잠김).
- iOS·Android 실기기는 아직 확인하지 않았다. 특히 iOS는 끝 방향을 `manualActivation`으로 잡는 경로가 웹과 다르다.

## 배운 점 / 재발 방지

**제스처 영역은 렌더 트리를 따른다.** "같이 밀리지 않게"라는 시각적 요구를 "페이저 밖에 둔다"로 옮겼는데, RNGH에서 페이저 밖은 곧 **제스처 밖**이다. 보이는 위치와 터치를 받는 영역이 같은 결정으로 묶여 있다는 걸 놓쳤다. 떠 있는 UI를 제스처 컨테이너 위에 얹을 땐, 그 위에서 시작한 제스처가 어디로 가야 하는지부터 정해야 한다.

**절대배치는 부모 크기를 만들지 않는다.** 페이저 같은 구조를 원래 흐름 배치이던 화면에 씌우면, 그 화면을 높이 없이 끼워 쓰던 곳이 조용히 0이 된다. 바꾸기 전에 그 컴포넌트를 **어디서 끼워 쓰는지** 전부 찾아야 했다(`<HouseScreen` 검색 4곳).

**단위 테스트는 제스처 핸들러를 직접 부른다 — 터치가 거기까지 가는지는 모른다.** 1번은 핸들러 로직이 아니라 "터치가 핸들러에 닿느냐"의 문제라 jest로는 원리적으로 못 잡는다. 제스처 작업은 실제 포인터로 한 번은 끌어 봐야 한다. 고친 뒤엔 "레일이 페이저 영역 안, 미끄러지는 줄 밖에 있다"를 구조 테스트로 잠갔다.

**재사용은 옵션의 기본값을 지키는 데서 성립한다.** 탭 페이저를 고치는 대신 옵션을 더하고, 기본값에서 기존 테스트 41건이 그대로 통과하는 걸 먼저 확인한 뒤 진행했다. 쌓여 있던 플랫폼 수정 세 가지를 하나도 다시 밟지 않았다.
