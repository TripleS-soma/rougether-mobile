# 방 꾸미기 편집기에서 방을 건드릴 때마다 카탈로그 전체가 다시 그려지던 문제 — memo 경계와 참조 안정성

- 2026-08-13 / room / #794, PR #795 (후속: #934·PR #935, #1201, #1275)
- 키워드: 편집기 성능, 리렌더 경계(React.memo), 콜백 참조 안정성(useStableCallback), 캔버스와 패널 분리, 렌더 횟수 회귀 테스트, 측정 기반 최적화

## 배경

방 꾸미기 화면은 작은 디자인 편집기다. 위쪽 **캔버스**에서는 방에 놓인 가구를 탭해 고르고, 끌어 옮기고, 크기를 바꾼다.
아래쪽 **패널**은 카탈로그 그리드다. 가구·벽지·바닥·배경 타일을 골라 방에 넣는다. 두 영역은 한 화면 컴포넌트
(`room-decor-screen.tsx`)의 상태를 함께 쓴다. 실서버 카탈로그는 189종(positioned 122 / surface 42 / character 25)이다.

## 문제 (증상)

캔버스에서 무엇을 하든 패널의 타일이 전부 다시 렌더됐다. 가구 선택, 드래그 커밋, 스케일 변경, 툴바 조작이 모두 해당됐다.
방 가구 몇 개만 다시 그리면 되는 조작인데 카탈로그 전체가 함께 그려졌다.

렌더 횟수를 세어 보니(로컬 데모 카탈로그 10종, 방 가구 2개) 방 안 가구를 **한 번 선택할 때 타일 렌더가 12회**
추가로 일어났다. 카탈로그 10장과 방 가구 2개다. 실서버 카탈로그는 이보다 훨씬 크므로 기기에서는 격차가 더 커진다.
다만 기기에서 프레임이나 ms를 따로 재지는 않았다.

## 원인 분석 (가설 → 검증 과정)

1. **경계가 없다.** `SwatchGrid` / `SwatchTile` / `FurnitureGrid` / `FurnitureTile` / `ClearTile`이 모두
   memo 없는 순수 함수 컴포넌트였다. 부모 화면이 다시 그려지면 그리드도 무조건 따라 그려졌다.
2. **memo만 붙여서는 소용이 없다.** 그리드로 내려가는 콜백 12곳이 모두 인라인 람다였다
   (`onSelect={(id) => setWallpaperId(id)}` 등). memo를 붙여도 렌더마다 새 함수가 내려가 얕은 비교가 실패한다.
   그래서 "경계 + 참조 고정"을 한 묶음으로 봐야 했다.
3. **타일 하나의 비용도 컸다.** `active={placed.includes(item.id)}` 때문에 타일마다 배열을 O(n)으로 훑었다.
   카탈로그 크기의 제곱이다. PR에서는 가구 122종이면 선택 한 번에 약 1.5만 회 비교가 된다고 계산했다(122² 계산값이며 실측은 아니다).
4. **리뷰에서 넷째 함정이 나왔다.** `floors`/`backgrounds`의 기본 파라미터가 `= []`였다. prop을 넘기지 않는 호출자에서는
   렌더마다 새 배열이 생겼다. 그러면 `owned`, 정렬 memo, 그리드 memo가 차례로 무효화된다. 운영 호출자(`app-shell`)는
   안정 참조를 넘겨서 겉으로 드러나지 않았다. 하지만 이 PR의 새 테스트가 바로 그 경로를 타고 있었다.

## 해결

- 그리드와 타일 5종에 `React.memo` 경계를 세웠다.
- 그리드로 내려가는 인라인 람다 12곳을 `useStableCallback`으로 바꿨다. 이 훅은 참조가 고정된 함수를 돌려주고,
  최신 클로저는 ref로 읽는다. 그래서 `togglePlace`가 최신 `placedSet`을 읽어도 stale 값 문제가 없다.
- `placed` 조회를 `Set`으로 바꿨다(O(1)). 그에 맞춰 `FurnitureGrid`의 `placed` prop 타입을 `string[]`에서 `Set<string>`으로 바꿨다.
- 기본값 `[]`을 모듈 상수 `NO_SURFACES`로 올렸다. 왜 상수여야 하는지는 주석으로 남겼다.
- **회귀 테스트는 렌더 횟수를 직접 단언한다**(`room-decor-catalog-perf.test.tsx`). 타일 리프(`FurniturePlaceholder`)를
  카운터로 모킹하고, 가구 탭 제스처를 실제로 발사한다. 그 뒤 추가 렌더가 방 가구 수(2) 이하인지 본다. 처음 쓴 느슨한
  단언(`afterSelect < afterMount`)은 최적화 없이도 통과했다. 그래서 폐기하고 다시 썼다. 최적화 커밋만 되돌리면
  `Expected: <= 2 / Received: 12`로 실패하는 것을 확인했다. 같은 파일의 둘째 테스트는 `placedSet` 배선을 맡는다.
  방에 있는 가구 타일이 `selected`로 뜨고, 그 타일을 누르면 방에서 빠지는지 확인한다.

| -------------------------------- | ------------------------- |
| 수정 전                          | 12회 (카탈로그 10 + 방 2) |
| 수정 후                          | 2회 (방 가구만)           |

## 배운 점 / 재발 방지

- **memo는 혼자 일하지 않는다.** 경계(memo)와 입력의 참조 안정성(콜백·배열·객체)이 함께 있어야 bail-out이 된다.
  인라인 람다 하나, 기본 파라미터 `[]` 하나로도 경계 전체가 무력해진다.
- **편집기는 캔버스 상태와 패널 상태의 경계를 렌더 단위로 나눠야 한다.** 캔버스 조작(선택·드래그)은 패널을 다시 그릴 이유가 없다.
  두 영역이 한 컴포넌트의 상태를 공유하더라도, 패널로 내려가는 prop이 바뀌지 않으면 패널이 다시 그려지지 않게 해야 한다.
- **최적화는 숫자로 못 박는다.** 체감으로 끝내지 않고 렌더 횟수나 ms/commit을 잰다. 회귀 테스트는 **최적화를 되돌렸을 때 실제로
  실패하는지** 확인한 뒤에만 믿는다. 느슨한 단언은 최적화 없이도 통과하는 일이 실제로 있었다.
- 리팩터링(파일 분리, JSX 접기)을 할 때는 이 렌더 횟수 테스트가 경계 보존을 지키는 안전망 역할을 했다.
