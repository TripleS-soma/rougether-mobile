# 기기 없이 폴더블 대응하기 — 웹 E2E로 배치 규칙을 잠그고, 실기기 캡처로 틀린 가정을 잡기

- 2026-11-19 ~ 2026-11-23 / design·infra / #1790 #1792 #1794 #1795 #1798~#1812
- 키워드: Playwright, 안전 영역(safe area), 반응형 2단 레이아웃, 테스트 주도 개발, React Native Web, 시뮬레이터 검증

## 배경

접었다 펴는 아이폰(Duo)과 갤럭시 Z 폴드를 제대로 지원해야 했다. 손에 기기가 없었다. 화면은 전부 폰 폭(약 390)을 전제로 그려져 있었고, 넓은 창에서는 가운데 폭 480의 기둥 안에 가두는 방식이었다(#1785). 펼친 화면(951×669)에서는 폭 951 중 480만 쓰고 나머지가 비었다.

요구는 두 가지였다. 접힌 화면(466×678, 넓고 짧음)에서 그림이 화면을 삼키지 않을 것, 펼친 화면에서 탭이든 아니든 모든 화면이 여백 없이 창을 채울 것.

## 문제 (증상)

1. **볼 수 없는 것을 고쳐야 했다.** 기기가 없으니 "어긋났는지"부터 알 수 없었다.
2. **대상이 많았다.** 탭 5개와 탭이 아닌 화면 약 40개.
3. **웹과 실기기가 달랐다.** 나중에 드러난 것인데, 웹 E2E가 전부 통과한 상태에서 실기기 시뮬레이터를 펼쳐 보니 세 가지가 틀려 있었다(아래).

## 원인 분석 (가설 → 검증 과정)

**먼저 "맞는 배치"를 숫자로 정했다.** 스크린샷 비교는 폰트·이미지 로딩에 흔들리고, 무엇이 틀렸는지 말해 주지 않는다. 그래서 요소의 위치·크기를 읽어 단언하는 규칙 여섯 개를 만들었다: 조작 요소가 시스템 표시 영역과 겹치지 않는다, 모달의 닫기 버튼이 화면 안에 있다, 방·집 그림의 가로세로 비가 계약 값과 1% 안에서 같다, 펼친 화면에서 칸들의 폭 합이 창 폭과 같다, 핵심 내용이 첫 화면 안에 있다, 가로 스크롤이 없다.

Playwright에 화면 크기 프로젝트 네 개(폰 402×874, 접힌 Duo, 펼친 Duo, 데스크톱 1280×800)를 두고, API는 전부 가로채 고정 응답으로 돌렸다. 서버와 실계정에 닿지 않게 네트워크 가드도 걸었다(웹소켓·팝업 포함).

**안전 영역은 웹에서 재현되지 않는다.** Chrome DevTools Protocol의 `Emulation.setSafeAreaInsetsOverride`로 `env(safe-area-inset-*)`를 주입했다. 주입할 값은 시뮬레이터에서 쟀다.

**여기서 가정 하나가 틀렸다.** 접힌 Duo에서 잰 값(위 0 · 오른쪽 84 · 아래 34)을 펼친 화면에도 그대로 적었다. 펼친 화면의 웹 E2E는 그 값으로 전부 통과했다. 시뮬레이터를 실제로 펼쳐 캡처하니 화면 위쪽이 통째로 비고 방 그림이 탭 바 밑으로 밀려 있었다. 앱 화면에 `useSafeAreaInsets()` 값을 글자로 찍는 임시 묶음을 올려 다시 쟀다: **위 82 · 오른쪽 0 · 아래 34**. 시스템 표시(시계·와이파이)는 오른쪽 위 모서리에만 있는데, iOS는 위쪽 전체 폭을 비우라고 알려 준다.

같은 캡처에서 두 가지가 더 나왔다.

- 달력 탭의 오른쪽 칸이 비어 있었다. 앱은 날짜를 누르면 주간 보기로 넘어가게 돼 있어 월 달력 아래에 목록을 그리지 않는다. 웹은 목록을 그대로 두는 분기라 웹 E2E로는 볼 수 없는 차이였다.
- 왼쪽 칸의 제목 알약 글자가 아주 작게 찌그러졌다. 위 여백을 0으로 둔 것이 조건이었다. 여백만 바꿔 가며 세 번 찍어 좁혔다: 0은 깨지고 16·24는 정상. 정확한 원인(iOS 27 글래스 면과 화면 끝의 관계로 추정)은 끝까지 좁히지 못했다.

**시뮬레이터에 새 코드를 올리는 길도 막혀 있었다.** 설치본은 JS가 앱 안에 든 빌드라 개발 서버를 보지 않았고, 네이티브 재빌드는 한 번에 수 분이 걸린다. `expo export:embed`로 JS 묶음만 만들어 설치된 앱 안의 `main.jsbundle`과 바꿔 치우는 방법으로 재빌드 없이 확인했다. 터치 입력은 넣을 수 없어서, 시작 탭 저장값을 바꾸거나 시작 화면을 고정한 임시 묶음으로 보고 싶은 화면을 띄웠다.

## 해결

**접힌 화면.** 가로 안전 영역은 화면마다 피하지 않고 앱 프레임 한 곳이 비운다. 넓고 짧은 화면(폭/높이 ≥ 0.5)에서는 그림 높이를 화면 절반에 맞추고, 방 양옆은 같은 벽지·바닥 그림을 흐리게 깔아 잇는다(서버가 주는 벽지 색은 그림과 무관한 색조라 단색으로는 경계가 드러났다).

**펼친 화면.** 터치 기기는 배치 폭 640 이상이면 두 칸 1:1로 창을 다 쓴다. 탭 바는 폭 840 이상에서 왼쪽 세로 줄이 된다. 왼쪽 칸은 위쪽 안전 영역을 통째로 비우지 않고(16만), 오른쪽 칸은 시스템 값보다 16 더 내린다. 와이파이 그림이 시스템 인셋(82)보다 낮은 98pt까지 내려와 있었기 때문이다.

**탭이 아닌 화면 35개.** 처음 계획은 화면마다 넓은 배치로 다시 짜는 것이었다. 실제로는 화면 상태와 뒤로가기 맵을 그대로 두고 **그리는 자리만** 바꿨다. `splitPaneHost(screen)`이 그 화면을 품을 탭을 돌려주면, 셸은 층과 페이저에는 그 탭 화면으로 보이게 하고 서브화면 노드는 탭 화면의 오른쪽 칸 위에 덮어 그린다. 화면 코드는 한 줄도 고치지 않고 설정·구성원 관리·루틴 관리·알림함 등이 칸에 열린다. 앱 셸 밖에 있는 로그인·온보딩만 왼쪽을 앱 소개로 채우는 별도 틀을 썼다.

**실패 예상 테스트.** 고치기 전의 결함은 `test.fail()`로 잠가 두었다. 그대로면 초록이고, 누가 고치면 "예상과 달리 통과"로 빨갛게 바뀌어 표시를 지우라고 알려 준다. 접힌 Duo의 결함 8건을 이렇게 잠근 뒤 하나씩 일반 테스트로 바꿨다.

## 결과 (수치)

- PR 19개(#1790, #1792, #1794, #1795, #1798~#1812) 전부 머지 — JS만 바꿨고 네이티브 지문 변화 없음.
- 웹 E2E: 0 → 102개. 전체 실행 약 43초(로컬, 4개 화면 크기).
- 단위 테스트: 4,090 → 4,161개.
- 접힌 Duo의 결함 8건 해소. 펼친 Duo에서 다섯 탭과 하위 화면 35개, 가입 흐름 5개 화면이 창 폭을 다 쓴다.
- 실기기 캡처로만 드러난 문제 5건: 펼친 화면의 안전 영역 값, 달력의 빈 오른쪽 칸, 찌그러진 제목 글자, 좌석 이름표 잘림, 와이파이 그림과 겹친 머리 버튼.
- 시뮬레이터 확인은 네이티브 재빌드 없이 JS 묶음 교체로 했다(걸린 시간은 따로 재지 않았다).

## 배운 점 / 재발 방지

- **테스트가 통과한다는 것은 "넣어 준 가정 아래에서 맞다"는 뜻이다.** 펼친 화면의 E2E는 틀린 인셋을 주입받고 전부 초록이었다. 주입값은 조건마다 따로 재야 하고, 잰 방법과 날짜를 값 옆에 적어 둔다.
- **웹 E2E는 싸고 빠른 대신 플랫폼 분기를 못 본다.** `Platform.OS`로 갈리는 동작(달력의 주간 보기)은 웹에서 통과해도 앱에서 다를 수 있다. 화면 크기마다 실기기 캡처를 적어도 한 번은 본다.
- **값을 화면에 찍는 것이 가장 확실한 측정이었다.** 확인용 앱을 따로 만든 것보다, 실제 앱에 한 줄을 넣은 임시 묶음이 빨랐고 틀릴 여지가 없었다.
- **화면 40개를 고치는 일이 "그리는 자리를 바꾸는 일" 하나로 줄었다.** 화면을 다시 짜기 전에, 화면이 놓이는 틀을 바꿀 수 있는지 먼저 본다.
- 한계: 시뮬레이터에 터치를 넣지 못해 누르는 동작은 웹 E2E와 단위 테스트로만 확인했다. 갤럭시 Z 폴드는 아직 화면 크기를 재지 않았다.
