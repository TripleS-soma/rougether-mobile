# 심사 제출된 테스트 빌드가 개발 OTA를 받는 문제 — EAS 채널 재배선

- 2026-09-16 / infra(OTA·릴리스 운영) / #1373
- 키워드: EAS Update 채널·브랜치 매핑, expo-updates, App Store 심사, 릴리스 레인 분리, 무중단 운영 대응

## 배경

EAS Update는 **채널이 바이너리에 박히고, 채널이 어느 브랜치의 업데이트를 받을지는 서버에서 바꿀 수 있다.** 이 프로젝트는 레인을 둘로 나눠 운영한다.

- 개발 레인: `testflight`·`preview` 프로필 빌드(채널 `dev`) — dev 브랜치 머지마다 OTA 자동 발행
- 스토어 레인: `production` 프로필 빌드(채널 `production`) — main 승격 후 수동 발행

## 문제 (증상)

1.5.3 iOS를 App Store 심사에 올리면서 스토어용 production 빌드가 아니라 **TestFlight 테스트 빌드 125(채널 `dev`)** 가 제출됐다. 이 상태로 두면:

- dev에 PR이 머지될 때마다 심사 중인 바이너리가 새 JS를 받는다 → 제출본과 다른 코드가 심사대에 오름(거절 사유 가능)
- 출시 후에는 스토어 사용자 전원이 검증 안 된 개발 레인 코드를 받는다

실제로 확인 시점에 dev 채널의 마지막 업데이트가 이미 dev 브랜치 머지분이었고, 곧 머지될 JS 변경 PR들이 대기 중이었다.

## 원인 분석

- 스토어 제출은 main의 production 프로필 빌드로만 한다는 규칙이 있었지만, App Store Connect의 "빌드 추가" 목록에 TestFlight 빌드도 똑같이 보여 구분이 안 된다(과거 1.4.0 빌드 111에서도 같은 일이 있었다).
- 바이너리를 바꾸려면 재빌드·재제출(수 시간~수일)이 필요하다. 반면 채널→브랜치 매핑은 서버 설정이라 즉시 바꿀 수 있다.

## 해결

바이너리는 그대로 두고 **채널 지도를 바꿨다.**

1. `dev` 채널 → `production` 브랜치: 빌드 125(및 같은 채널의 테스터 설치본)는 이제 스토어 레인 업데이트만 받는다.
2. 새 `internal` 채널 → `dev` 브랜치: 개발 레인의 새 이름.
3. `eas.json`의 `testflight`·`preview` 프로필 채널을 `internal`로 교체(#1373). `eas.json`은 지문 입력이 아님을 과거에 실측해 두었으므로 기존 설치본의 OTA가 끊기지 않는다. 테스트 빌드 가드 스크립트의 채널 상수도 함께 수정(CI 테스트 5건이 이걸 잡아냄).
4. **순서를 지켰다**: 채널 재배선 전에 JS 변경 PR이 dev에 머지되지 않도록 대기 중이던 PR을 드래프트로 되돌려 자동 머지를 막고, 재배선 확인 후 머지했다.

main 승격 후 main의 iOS 지문이 빌드 125와 같음(`0ed984cc`)을 확인해, 출시 후 핫픽스 OTA 경로도 살아 있게 했다.

## 결과 (수치)

- 재빌드·재제출 0회로 심사 빌드를 스토어 레인에 격리
- 채널 명령 3개 + 설정 PR 1개, 재배선 전 머지 차단 1건

## 배운 점 / 재발 방지

- OTA 사고는 "바이너리를 다시 낸다"보다 "채널 매핑을 바꾼다"가 훨씬 빠르고 안전한 경우가 많다. 채널=바이너리 고정, 브랜치=서버 가변이라는 구분이 핵심.
- 인프라 변경과 코드 머지의 **순서**가 사고를 만든다. 자동 머지가 걸린 PR이 있으면 먼저 멈춘다.
- 재발 방지는 문서(릴리스 런북 채널 지도·"channel이 production인 빌드만 제출")와 가드 스크립트로.
