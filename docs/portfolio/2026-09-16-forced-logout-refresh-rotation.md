# 하루에도 여러 번 로그인이 풀리는 문제 — 1회용 refresh 토큰 회전과 재사용 감지

- 2026-09-16 / member(인증) / #1388
- 키워드: JWT access/refresh, refresh token rotation, reuse detection, 동시성(백그라운드 작업·다중 탭), 관측 가능성(계측 먼저)

## 배경

인증은 access 토큰(HS256 JWT, 30분)과 refresh 토큰(불투명 랜덤, 14일)이다. refresh는 **1회용**이라 갱신할 때마다 새 쌍으로 바뀌고, 서버는 이미 사용된 refresh가 다시 오면 탈취로 간주해 **그 회원의 모든 refresh 토큰을 즉시 폐기**한다(유예 0초). 앱은 401을 받으면 갱신 후 1회 재요청하고, 갱신이 4xx로 거부되면 세션을 지워 로그인 화면으로 보낸다.

## 문제 (증상)

iOS·Android·웹 모두에서 "같은 기기인데 하루에도 여러 번 로그인 화면으로 나간다"는 보고. refresh 만료(14일)로는 설명되지 않는다.

## 원인 분석 (가설 → 검증 과정)

1. 서버 설정 확인: access 30분 / refresh 14일 → 만료 가설 배제.
2. 서버 `AuthService.refresh`: 폐기된 토큰의 재사용, 또는 동시 회전에서 진 경우(조건부 UPDATE 영향 행 0) 모두 `revokeAllActive(userId)` → **회원 단위 전체 폐기**.
3. 정상 사용 중 "재사용"이 생기는 경로를 앱 코드에서 찾음:
   - 서버는 회전을 커밋했는데 응답이 앱에 도착하기 전에 앱이 백그라운드로 가거나(iOS 일시정지), 네트워크가 끊기거나, 웹 탭이 닫힘 → 앱은 옛 토큰을 보관 → 다음 갱신이 재사용으로 판정.
   - access가 30분이라 갱신이 하루 수십 번 → 드문 사고도 누적된다.
   - Android 앱 아이콘 헤드리스 백그라운드 작업이 세션을 따로 읽어 API를 부르고, 401이면 **자체 메모리의 refresh로 회전** → 앱 본체와 동시 회전 경합.
   - 폐기가 회원 단위라, 앱과 웹을 같이 쓰면 한 기기의 사고가 다른 기기까지 로그아웃시킴(이슈의 "전 플랫폼" 증상과 일치).
4. 과거에 같은 계열 사고를 두 번 막았음: 동시 401의 단일 비행(#515), 웹 다중 탭의 저장소 재확인·Web Locks(#1262). 이번엔 **실행 맥락이 다른** 경로(헤드리스 작업)와 **응답 유실** 경로가 남아 있었다.
5. 앱이 강제 로그아웃의 원인을 기록하지 않아 위 가설을 데이터로 확인할 수 없었다 → 서버 정책 변경 전에 **계측부터**.

## 해결 (1단계, 앱)

- 강제 로그아웃 계측: 갱신 거부로 세션이 지워질 때 `session_forced_logout`(reason·status·서버 오류 코드·foreground/background)을 GA4와 Sentry에 남긴다. 사용자가 누른 로그아웃·탈퇴는 이유를 분리해 세지 않는다.
- 거부 후 채택: 갱신이 4xx로 거부돼도, 우리가 보낸 refresh와 **다른** 쌍이 저장소에 있으면 다른 맥락이 먼저 회전한 것이므로 그 쌍을 채택하고 로그아웃하지 않는다(`session_refresh_adopted`로 계측).
- 헤드리스 백그라운드는 토큰을 회전하지 않는다: 요청 옵션 `refreshOnUnauthorized: false`를 추가해 앱 아이콘 백그라운드 조회에 적용. 만료면 조용히 건너뛰고 앱이 켜질 때 갱신한다.

## 결과 (수치)

- 인증·API·훅·셸 관련 114 suites / 784 tests 통과, 신규 테스트 3건(거부 후 채택, 거부 시 계측, 백그라운드 무회전).
- 강제 로그아웃 빈도·경로 데이터: 배포 후 수집 예정(후속에 기록).

## 배운 점 / 재발 방지

- 보안 정책(재사용 감지 즉시 전체 폐기)과 모바일 네트워크 현실(응답 유실은 흔함)이 충돌하면 사용자에게는 "로그인이 자꾸 풀린다"로 보인다. 업계는 짧은 유예 시간(reuse interval)과 기기(토큰 체인) 단위 폐기로 절충한다 — 서버 변경은 계측 데이터를 본 뒤 결정하기로 함.
- 원인을 확정할 데이터가 없을 때는 고치기 전에 **계측을 먼저** 싣는다. "추정으로 서버 보안 정책을 완화"하는 것보다 싸고 되돌릴 필요가 없다.
- 1회용 토큰을 쓰는 코드는 **실행 맥락(프로세스·탭·헤드리스 작업) 수만큼** 경합 지점이 생긴다. 새 백그라운드 작업을 추가할 때 인증 갱신을 할지 반드시 정한다.
