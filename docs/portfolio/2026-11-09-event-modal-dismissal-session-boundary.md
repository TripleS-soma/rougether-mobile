# 이벤트 모달의 닫힘 완료와 계정 전환 경계를 분리한 사례

- 날짜: 2026-11-09
- 영역: 모바일 이벤트, iOS 모달, 계정별 서버 상태
- 관련 변경: 크리스마스 누적 출석과 이벤트 안내 연결
- 키워드: React Native Modal, onDismiss, 비동기 경쟁, 계정별 캐시, 멱등 요청

## 배경

습관 형성을 돕는 소셜 루틴 앱에 누적 출석판과 이벤트 안내를 연결했다. 로그인과 온보딩 뒤 현재 화면 위에 출석판을 먼저 표시하고, 보상 연출과 닫힘이 끝난 다음 안내를 표시해야 했다. 기존 출석, 신고, 제작 가구 판매 시트도 같은 앱에서 동작하므로 새 이벤트만 순서를 지켜서는 충분하지 않았다.

## 문제 (증상)

처음에는 공용 BottomSheet의 200ms 퇴장 애니메이션이 끝나면 화면이 닫혔다고 판단했다. 리뷰에서 이 시점과 iOS의 native Modal 해제 완료가 다르다는 점을 확인했다. 새 이벤트를 이 사이에 열면 이전 native 화면이 남은 상태에서 다음 화면을 표시할 수 있었다.

계정 전환도 별도의 비동기 경계였다. 출석 응답이 늦게 도착하거나 응답 유실 뒤 상태를 재조회할 때, 요청을 시작한 계정과 현재 계정이 다를 수 있었다. 이는 리뷰로 찾은 위험이며 실제 사용자 데이터 오염 사고를 확인한 것은 아니다.

## 원인 분석 (가설 → 검증 과정)

JS의 표시 상태, 퇴장 애니메이션 종료, native 화면 해제를 하나의 상태로 취급한 것이 모달 순서 문제의 원인이었다. 공용 시트에 `onDismiss`가 없어 다른 화면은 native 해제 완료를 기다릴 방법이 없었다.

`mounted`와 `rendered`를 분리한 뒤 전체 테스트에서 신고, 제작 가구 판매, 달력 입력 왕복의 다섯 테스트가 실패했다. 테스트들은 퇴장 시간만 흐르면 다음 화면이 열린다고 가정했고 native `onDismiss`를 보내지 않았다. 각 흐름에서 실제 콜백을 보관하고 퇴장 후 명시적으로 호출해 다음 화면이 열리는지 확인했다.

계정 경계는 요청을 지연시킨 상태에서 계정을 바꾸는 테스트로 검증했다. 출석 성공과 실패, 영구 숨김, 이벤트 재조회에서 이전 계정의 후속 요청이나 응답이 새 계정의 지갑, 캐시, 화면에 반영되지 않아야 했다.

## 해결

- iOS에서는 Modal을 `visible=false` 상태로 유지하고 native `onDismiss`가 온 뒤에만 존재 상태와 다음 시트 대기열을 해제했다. Android와 웹은 다음 프레임에 해제한다.
- 이벤트는 단일 활성 화면으로 관리하고 출석 보상 연출과 native 닫힘 완료 뒤 공지를 표시한다. 기존 시트가 열려 있거나 닫히는 중이면 이벤트가 기다린다.
- 계정별 이벤트 캐시 키를 유지하고 요청 전후 세션 사용자를 비교했다. 계정이 바뀌면 이전 출석의 후속 GET, 지갑 갱신, 영구 숨김 캐시 갱신과 보상 연출을 중단한다.
- 출석 POST는 자동 재시도하지 않는다. 응답 유실은 같은 이벤트의 서버 상태와 지갑, 보유함을 재조회해 수렴시킨다.

## 결과 (수치)

계정 전환과 이벤트 큐의 16개 테스트는 강제 종료 없이 통과했다. 모달 해제와 뽑기 초기 선택의 회귀 테스트 57개도 통과했다. native 콜백을 반영한 기존 네 스위트의 63개 테스트도 통과했다. 이 수치는 소스와 테스트 검증이며, iOS 실제 기기에서 native 전환을 검증하거나 운영 이벤트를 공개했다는 의미는 아니다.

## 배운 점 / 재발 방지

애니메이션 종료는 플랫폼 자원의 해제 완료가 아니다. 다음 화면을 여는 조건을 실제 수명주기 콜백에 연결하고 테스트도 같은 콜백을 재현해야 한다. 계정별 캐시 키만으로는 진행 중 요청의 계정 전환을 막지 못하므로, 요청 후 처리와 복구 요청에도 세션 경계를 확인해야 한다.

## 후속: 크리스마스 3일차 캐릭터 수령 (2026-11-11)

습관 형성을 돕는 소셜 루틴 앱에서 이미 출석을 마친 계정에도 신규 캐릭터를 지급해야 했다. 출석 요청을 대신 보내면 오늘 코인과 출석 기록까지 바뀌므로, 캐릭터만 수령하는 별도 POST를 연결했다. 실패 뒤에는 같은 이벤트를 GET으로 확인하고 자동 POST 재시도를 막았다. 서버 응답이 유실되기 전과 후를 나눠 복구와 수동 재시도를 검사했다.

계정 A의 수령이 진행 중일 때 계정 B로 바뀌면, 공유 잠금 때문에 B의 자동 수령이 시작되지 않을 수 있다. 시도 이력을 기록하기 전에 잠금을 확인하고, 요청 정리가 끝난 상태를 React state에도 반영해 B의 수령 조건을 다시 평가하게 했다. 테스트에서 A의 응답이 B의 캐시를 갱신하지 않고, A의 정리 후 B가 자기 수령 요청을 보내는지 확인했다. 이 결과는 로컬 훅 테스트이며 실제 사용자 지급이나 운영 배포 완료의 증거는 아니다.
