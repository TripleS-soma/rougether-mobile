# 테스트·빌드·업로드를 다 통과한 iOS 빌드가 켜자마자 꺼진 문제 — 입력이 아니라 산출물을 검사하기

- 2026-08-19 / infra(릴리스 검증)·member(캘린더 가져오기) / #880(원인 유입), #913(이슈), #914(수정), #915·#933(산출물 검사), #1684·#1688(오픈소스 CLI로 이전)
- 키워드: Expo config plugin, CNG(prebuild) 산출물, Info.plist 권한 키, AndroidManifest 병합(`tools:node="remove"`), 바이너리 diff, 오픈소스 CLI

## 배경

1.2.0에서 기기 캘린더 가져오기(#844)를 붙였다. 앱은 캘린더를 읽기만 하므로 "안 쓰는 권한은 선언하지 않는다"는 취지로 config plugin(`plugins/with-calendar-readonly.js`)을 만들어, iOS에서는 미리알림 권한 키를, Android에서는 `WRITE_CALENDAR`를 걷어냈다.

## 문제 (증상)

iOS 1.2.0(빌드 47)이 TestFlight에서 스플래시만 잠깐 보이고 즉시 종료됐다. 1.1.0(빌드 43)은 정상. 이 빌드는 EAS 빌드 성공, CI(테스트 990개) 통과, App Store Connect 업로드 성공을 모두 거쳤다. 직접 켜 보지 않았다면 심사에서 애플이 발견했을 것이다.

크래시 로그는 `EXC_BREAKPOINT`, 잡히지 않은 Objective-C 예외, 큐 `expo.controller.errorRecoveryQueue`. Sentry에는 아무것도 없었다.

## 원인 분석 (가설 → 검증 과정)

1. 크래시 로그만으로는 범인이 보이지 않았다. 제출된 IPA를 직접 받아 UUID가 크래시 로그와 일치하는지 확인했다.
2. **빌드 43과 47의 번들을 통째로 비교**했다. 차이는 세 가지뿐: 버전 문자열, 빌드 번호, 그리고 `Info.plist`에서 `NSRemindersUsageDescription`·`NSRemindersFullAccessUsageDescription`이 사라진 것. 프레임워크·매니페스트·`Expo.plist`는 같았다.
3. 바이너리에서 `MissingRemindersPListValueException` 문자열을 찾고 `expo-calendar` 소스를 따라갔다. 모듈의 `OnCreate`(앱 시작)에서 미리알림 권한 상태를 조회하고, 키가 없으면 `RCTFatal`을 부른다. 캘린더 화면을 열지 않아도 100% 재현.
4. 같은 플러그인이 Android에서는 `WRITE_CALENDAR`를 지웠는데, `expo-calendar`는 READ·WRITE를 둘 다 요구해 권한이 영영 허용되지 않았다. 크래시 없이 기능만 조용히 죽는 고장이었다.
5. **놓친 이유**를 신호별로 적었다.
   - 테스트는 `app.json`(입력)을 봤다. 키를 지운 건 prebuild 때 도는 플러그인이었고, 망가진 건 산출물뿐이었다.
   - 네이티브 사전 검사 CI는 원인 PR(#880, `native-build` 라벨)에서도 돌아 통과했지만 Android 매니페스트 병합만 봤고 iOS `Info.plist`는 보지 않았다. 게다가 라벨 PR에서만 돌아서, 수정 PR(#914)은 처음에 라벨 없이 올라와 검사를 건너뛰었다(#915).
   - 크래시가 JS Sentry 초기화보다 먼저 났다. 네이티브 크래시는 다음 실행에 업로드되는데, 시작 크래시에는 다음 실행이 없다.

## 해결

- **핫픽스(#914)**: 플러그인을 고쳐 미리알림 키를 되돌리고(한국어 문구 포함), Android `WRITE_CALENDAR`를 복구. 권한 **선언**은 넓어지지만 **동작**은 그대로(읽기만, 미리알림 프롬프트 없음)임을 방침·문구에 맞췄다.
- **입력 쪽 가드**: `app-config-hygiene.test.ts`가 권한 문구 존재와 권한을 걷어내는 플러그인 금지를 강제하고, 주석에 이유를 남겼다.
- **산출물 쪽 가드(#933)**: CI에서 `expo prebuild --no-install` 후 생성된 `Info.plist`의 필수 키를 검사. **라벨 게이트를 일부러 걸지 않아** 모든 PR에서 돈다(수십 초). 생성된 plist에서 두 키를 지우면 실패하는 것을 재현으로 확인했다.
- **실행 확인**: 제출 전 사람이 실행해 보는 절차, 이후 Release 빌드를 시뮬레이터에 띄우는 `ios-release-smoke` 잡.
- **Android로 확장**: 소스 매니페스트에서는 금지 권한이 "없음"이 아니라 **제거 지시자(`tools:node="remove"`)가 붙어 있음**을 확인한다. `blockedPermissions`가 빠지면 그 줄이 사라지고 Gradle 병합 때 라이브러리에서 권한이 조용히 되살아나기 때문. 병합본에서는 `POST_NOTIFICATIONS`·`AD_ID`처럼 라이브러리가 넣는 필수 권한을 본다.

## 결과 (수치)

- 시작 크래시 원인을 번들 비교로 **차이 3건**까지 좁힘.
- 산출물 검사는 이후 iOS 필수 키 7개 + 금지 1개, Android 권한 규칙 15개(소스) + 병합 필수 2개, 대체 아이콘 5종, 런처 별칭 6개로 늘었다.
- 2026-11-08, 저장소 스크립트 3개를 오픈소스 CLI **[expo-release-guard](https://github.com/evan7484/expo-release-guard)** 로 옮겼다(0.1.0 → 0.3.0, 테스트 82개). 옮길 때마다 같은 산출물에 옛 스크립트와 새 CLI를 함께 돌려 결과가 같음을 확인했다. 일부러 망가뜨린 산출물(아이콘 누락·삭제·별칭 두 개 켜짐)에서 옛 스크립트는 첫 assert에서 멈췄고 CLI는 3건을 한 번에 보고했다.

## 배운 점 / 재발 방지

- **빌드 성공·테스트 통과·업로드 성공은 "켜지는가"에 대한 답이 아니다.** 신호마다 실제로 무엇을 보는지 적으면 구멍이 보인다.
- 입력과 산출물 사이에서 코드(config plugin)가 돈다. **산출물을 검사해야 한다.**
- **"없음"과 "조용함"은 안전 신호가 아니다**: 소스에 없는 권한, 비어 있는 Sentry.
- 비싼 검사는 라벨로 거르되, **싸고 치명적인 검사는 항상** 돌린다.
- 규칙에는 **이유**를 같이 둔다(CLI는 실패 메시지에 `reason`을 출력). 사고는 "이거 필요 없어 보이는데?"에서 시작했다.
