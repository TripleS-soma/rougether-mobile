# 방 꾸미기 편집기에 실행 취소·다시 실행 넣기 — 명령 패턴 대신 스냅샷 스택을 고른 이유

- 2026-11-05 / room / #1640
- 키워드: 실행 취소(undo/redo), 스냅샷 vs 명령(command) 패턴, 구조 공유, 히스토리 단위(coalescing), 더티 체크 연동, 제스처와 커밋 분리

## 배경

방 꾸미기 편집기는 가구 이동·크기·회전·반전·맨 앞/맨 뒤·빼기, 벽지·바닥·배경 선택을 지원하지만 **되돌리기가 없었다.** 가구를 잘못 빼거나 엉뚱한 곳에 놓으면 처음부터 다시 배치해야 했다. 편집 문서는 `items`(가구 배치)와 표면 3종(`wallpaperId`·`floorId`·`backgroundId`)으로 이뤄져 있었고, 이를 바꾸는 지점은 화면 안에 9군데(추가·빼기·드래그 놓기·크기·회전·반전·맨 앞·맨 뒤·표면 선택) 흩어져 있었다.

## 문제 (설계 질문)

1. 되돌리기를 **무엇으로 표현할까** — 동작마다 역연산을 두는 명령 패턴인가, 문서를 통째로 저장하는 스냅샷인가.
2. **한 단계는 무엇인가** — 드래그 한 번이 수십 단계가 되면 안 된다.
3. 기존 기능과 **어떻게 맞물릴까** — 선택 상태, "저장하지 않은 변경" 경고(더티 체크), 저장 충돌(409) 재로드.

## 원인 분석 (판단 과정)

**명령 패턴을 따져 봤다.** 동작마다 `do/undo`를 짜면 메모리는 적게 들지만, 맨 앞/맨 뒤처럼 **여러 가구의 z를 한꺼번에 바꾸는 동작**은 역연산에 이전 z를 전부 들고 있어야 한다. 9개 동작 각각에 역연산을 짜면 그만큼 되돌리기가 어긋날 자리도 생긴다.

**스냅샷의 비용을 따져 봤다.** 이 편집기의 모든 갱신은 이미 불변(immutable) 방식이었다(`prev.map(p => p.id === id ? {...p, x} : p)`). 그래서 스냅샷을 쌓아도 **바뀌지 않은 가구 객체는 이전 스냅샷과 같은 참조를 공유**한다. 가구 하나를 옮기면 새로 생기는 건 배열 하나와 객체 하나뿐이다. 문서도 작다(가구 수십 개). 스냅샷은 "그때 문서로 돌아간다"는 한 가지 연산뿐이라 틀릴 자리가 없다. → **스냅샷 스택(past / present / future)**으로 정했다.

**한 단계의 단위는 이미 정해져 있었다.** 드래그·핀치는 손가락이 움직이는 동안 UI 스레드의 Reanimated 값만 바뀌고, React 상태는 **놓는 순간 한 번만** 커밋된다([툴바 사례](2026-07-30-room-editor-toolbar-gesture.md)에서 리렌더가 진행 중인 제스처를 취소하는 문제 때문에 만든 구조). 그 커밋 지점을 히스토리 기록 지점으로 쓰면 드래그 하나가 자연스럽게 한 단계가 된다.

## 해결

- `decor-history.ts`: 순수 리듀서(`commit`·`undo`·`redo`·`reset`)와 훅 `useDecorHistory`를 만들었다.
  - **변화 없는 커밋은 쌓지 않는다**(`sameDoc` — 배열을 새로 만들었어도 내용이 같으면 같은 문서). 선택 없이 툴바를 누르거나 같은 벽지를 다시 고르면 "눌렀는데 아무 일도 안 일어나는 실행 취소 단계"가 생기기 때문이다.
  - 되돌린 뒤 새로 편집하면 다시 실행 기록을 버린다. 최대 50단계.
  - 훅이 돌려주는 함수는 모두 참조를 고정했다. 카탈로그 memo 경계([재렌더 사례](2026-08-13-room-editor-catalogue-rerender.md))를 뚫지 않기 위해서다.
- 화면은 기존 `setItems`·`setWallpaperId` 등 4개 setter의 **이름과 시그니처를 유지한 채** 히스토리 커밋으로 바꿨다. 9개 편집 지점은 손대지 않았다. 여러 값을 한 번에 바꾸는 "프리뷰 빼고 저장"만 4번 호출 대신 한 번의 커밋으로 묶었다.
- **선택 상태는 히스토리 밖에 둔다.** "선택만 바꾼 단계"가 끼면 되돌리기가 헛돈다. 대신 되돌려서 선택된 가구가 방에서 사라지면 선택을 푼다.
- **더티 체크는 그대로 연동된다.** "저장된 문서" 스냅샷과 현재 문서를 비교하는 기존 구조라서, 편집 후 처음 상태까지 되돌리면 "변경사항을 저장할까요?"가 뜨지 않는다. 저장 뒤 되돌리면 다시 "변경 있음"이 된다.
- 버튼(↶ ↷)은 화면에 고정된 플로팅 줄 오른쪽, 재화 알약 옆에 두고 되돌릴 게 없으면 비활성으로 표시한다. 처음엔 캔버스 오른쪽 위를 생각했지만, 그 자리에 이미 재화 알약이 떠 있어 겹치는 것을 코드에서 확인하고 옮겼다.

## 결과 (수치)

- 히스토리 리듀서 단위 테스트 7건: 왕복, 분기 시 다시 실행 기록 폐기, 변화 없는 커밋 무시, 50단계 상한, reset, **구조 공유**(바뀌지 않은 가구가 스냅샷 사이에서 같은 객체인지), `sameDoc`의 필드별 판정.
- 화면 테스트 2건: 빼기 → 실행 취소로 복귀 → 다시 실행으로 다시 빠짐(저장 값으로 확인) / 반전 후 되돌리면 뒤로가기 저장 확인이 안 뜸.
- 전체 jest 428 스위트 통과. 9개 편집 지점의 코드 변경 0줄(setter 시그니처 유지).
- 실기기에서 메모리·프레임은 재지 않았다. 50단계 × 가구 수십 개 규모라 문제될 크기는 아니라고 판단했다(추정).

## 배운 점 / 재발 방지

- 되돌리기 설계는 **"갱신이 이미 불변인가"**에서 갈린다. 불변이면 스냅샷이 거의 공짜다(구조 공유). 가변 객체를 직접 고치는 편집기였다면 명령 패턴이나 패치(diff) 기반을 골라야 했을 것이다.
- **히스토리 단위는 제스처 설계와 같은 문제다.** "놓을 때만 커밋"이라는 기존 성능 구조가 그대로 "드래그 한 번 = 한 단계"라는 사용자 기대와 맞았다.
- 다음 단계: 이 히스토리 위에 웹 키보드 단축키(`⌘Z`·`⌘⇧Z`), 드래그 중 스마트 가이드·스냅을 얹는다(아직 하지 않음).

## 후속

### 웹 키보드 단축키 (#1642, PR #1643)

같은 히스토리 위에 `⌘Z`/`⌘⇧Z`(Ctrl+Z/Y)·Delete·Esc·`⌘]`/`⌘[`·방향키 미세 이동을 얹었다. 새로 생긴 문제는 **방향키를 누르고 있으면 이동이 수십 번 커밋되는 것**이었다. 그대로 두면 실행 취소를 수십 번 눌러야 한다.

- 리듀서에 **묶음 키(coalescing)**를 더했다. 같은 키(`nudge:<가구>`)로 800ms 안에 이어진 커밋은 새 단계를 만들지 않고 현재 단계를 덮어쓴다. 실행 취소·다른 동작이 끼면 묶음이 끊긴다.
- 키 → 동작 매핑은 순수 함수로 분리했다(입력창 포커스 중 무시, 선택이 없으면 브라우저 기본 동작 유지).
- 웹에서 실측: 러그 선택 → `Shift+←` 3회 → `⌘Z` **한 번**에 원위치, 실행 취소 버튼 비활성·다시 실행 활성으로 전환(Chrome, Dev 갤러리).

### 스마트 가이드·스냅 (#1644)

드래그 중 다른 가구의 중심선·방 가운데 세로선 6px 안으로 들어오면 붙고, 붙은 축에 가이드 선을 그린다.

- **계산 위치가 핵심 판단이었다.** 드래그 중엔 React 상태를 바꾸면 제스처가 취소되므로([툴바 사례](2026-07-30-room-editor-toolbar-gesture.md)), 스냅 계산(`snapAxis`)을 팬 워클릿 안에서 매 프레임 돌리고 가이드 선 위치도 공유 값으로만 갱신했다. 가이드 선은 `transform`으로만 움직여 레이아웃 재계산이 없다. 드래그 중 리렌더는 여전히 0회다(구조상 보장, 프레임 측정은 하지 않음).
- **이동 가능 범위 밖 후보는 버린다.** 크기가 큰 가구는 방 가장자리 쪽 중심선에 닿을 수 없다. 그런 선에 붙이면 손을 뗄 때 클램프가 되돌려 "붙었다 튕기는" 모습이 된다.
- 새로 붙는 순간에만 선택 햅틱을 준다(붙어 있는 동안 매 프레임 울리지 않게).
- 검증: 스냅 단위 테스트 4건(임계 안·밖, 가까운 후보 우선, 범위 밖 후보 제외)과 후보 목록 1건, 화면 테스트 2건(320×384 방에서 중심선 4px 앞에 놓으면 정확히 0.65로 커밋 / 20px 이상 떨어지면 놓은 자리 그대로·손을 떼면 가이드 숨김). 웹 갤러리에서는 다른 항목의 시트가 화면을 덮어 드래그 실측을 못 했다.
