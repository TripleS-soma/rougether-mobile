# Align First — 구현 전 이해 확인·의논 루프

지시를 받자마자 코드를 고치지 않는다. **재진술 → 근거 확인 → 질문 → 합의 요약**을
거친 뒤에 작업을 시작한다. 목표는 "만들고 나서 아닌데?"를 없애는 것.

## 절차

1. **먼저 관련 코드·스펙을 확인한다.** 질문은 근거 위에서만 한다.
   - 해당 화면/어댑터/훅의 현재 동작 (실제 파일을 열어 확인)
   - `../rougether-spec`의 해당 도메인 문서와 서버 API 유무 — "서버에 없어서
     로컬 저장/PendingNotice로 가야 한다" 같은 제약은 질문 전에 파악해 선택지에 반영
2. **이해한 내용을 내 말로 재진술한다.** "현재 동작 → 원하시는 것" 구조로,
   파일:라인 근거와 함께. 지시와 코드 현실이 어긋나면 그 지점을 짚는다.
3. **결정이 필요한 디테일만 AskUserQuestion으로 묻는다** (한 번에 2~4개).
   - 각 질문은 상호배타적 옵션 + 추천안에 "(추천)" 표시와 그 이유
   - UI 배치·레이아웃처럼 시각적 비교가 필요하면 옵션에 **ASCII 목업 preview**를 붙인다
   - 관례적 기본값이 있거나 코드에서 답을 찾을 수 있는 건 묻지 말고 정해서 진행하되,
     재진술에 한 줄로 명시한다
   - 사용자가 "Other"로 되물으면 그 지점을 다시 정리해 후속 질문으로 좁힌다
4. **합의를 번호 목록으로 요약**하고, 그 다음에야 레포 워크플로(이슈 → `main`에서
   브랜치 → 구현 → 4종 체크·검증 → PR)로 넘어간다. 합의 요약이 곧 이슈 본문의
   골격이 된다.
5. **작업 중 전제가 깨지면 즉시 멈추고 다시 의논한다.** 예: 다른 PR 머지로 같은
   파일이 크게 바뀜, 서버 API 부재 발견, 합의한 설계가 기존 구조와 충돌. 발견한
   사실 → 영향 → 제안 순으로 짧게 보고하고, 방향 결정이 필요하면 다시 질문한다.

## 건너뛰는 경우

- 단순 버그 수정, 오타, 지시가 이미 파일·동작 단위로 구체적인 경우 → 바로 구현
- 사용자가 이미 상세 스펙(옵션까지)을 준 경우 → 재진술 한 단락으로 확인만 하고 진행
- 이 스킬을 이유로 뻔한 질문을 만들어내지 말 것 — 질문 수보다 질문의 질

## 예시 (실제 세션: #277 정원 기준 방 타일)

- 재진술: "타일이 실제 멤버 수만큼만 생성됨(`adapters.ts:559`) → 정원 기준
  고정 그리드로, 빈 자리는 같은 크기의 빈 타일로"
- 질문 1라운드: 빈 슬롯 UI(초대 유도 vs 조용한 빈방, ASCII 목업), 홀수 정원 처리,
  빈 슬롯 위치 → 사용자가 3번에서 "Other"로 새 요구(드래그 배치) 제시
- 근거 확인 후 2라운드: 기본 멤버 순서, 드래그 방식(swap vs insert), PR 분리
- 합의 요약 → 이슈 2개(#277, #278) → 구현
